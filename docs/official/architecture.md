# 架构约定

## Package 边界

- **@spherse/core**：纯 Node.js 核心逻辑，负责项目数据、agent profile、session、skill、tool 和运行时管理，不依赖 Electron 或 Fastify
- **@spherse/presets**：内置模板与预置静态内容，构建前通过 `scripts/sync-templates.mjs` 将 `templates/*.md` 同步为可导入常量，并从 `presets.json` 及 `skills/` 目录生成预置 skill 源码、agent 配置和 prompt template（`PRESET_SKILLS`、`PRESET_AGENTS`、`PRESET_SKILL_SOURCES`、`PRESET_PROMPT_TEMPLATES`）；其中 `PRESET_SKILL_SOURCES` 由 core 的 `SkillStore` 在内存中合并为 builtin skill，`PRESET_AGENTS` 供 `initPresets()` 在新项目创建时注入，`PRESET_PROMPT_TEMPLATES` 供前端 Agent 创建对话框作为可复用 prompt 模板徽章选择（不参与项目创建注入）
- **@spherse/server**：Fastify API 层，只负责把 HTTP/WebSocket 请求转发到 core 的运行时模块（ProjectManager、SessionRuntime、TriggerManager）
- **前端三层分离**：`@spherse/app`（共享 React renderer，含 features/stores/lib/components 与 `HostBridge` 接口）+ `@spherse/desktop`（Electron 桌面壳，main/preload/electron 基础设施 + 桌面专属 feature，提供 `ElectronHostBridge`）+ `@spherse/web`（移动端 PWA 壳，提供 `WebHostBridge`，经 Cloudflare Quick Tunnel 远程连接桌面 server）。renderer 通过 `HostBridge` 抽象访问宿主能力（IPC/外部链接/更新等），不直接 `window.electronAPI`，从而可在桌面与 Web 两种宿主复用。`HostBridge.capabilities: HostCapabilities` 声明各宿主的能力开关（`projectManagement`/`filePicker`/`appUpdate`/`devTools`/`mobileAccess`/`openFileExternal`/`settings.editable`/`content.editable` 等），renderer 据此条件渲染宿主专属 UI——如 Content Browser 的二进制文件占位卡「用默认应用打开」按钮仅当 `openFileExternal:true`（桌面端）显示，Web 端该能力为 `false` 不显示

## Core 层

- **运行时模块架构**：core 对外暴露职责清晰的运行时模块，由 `createProject` factory 创建并组装为 `ProjectRuntime`——`ProjectManager`（项目数据操作门面，包装 ProjectStore）、`SessionRuntime`（活跃 Agent 实例管理）、`TriggerManager`（trigger 配置读取与触发执行）与 `TimerService`（10 分钟轮询，驱动时间触发）。`ProjectRuntime` 是轻量协调层，只在操作跨越模块边界时介入（deleteSession、deleteAgent、shutdown）
- **导出收紧**：store 层只导出 `ProjectStore`（供 core 内部使用），其余 store 类不对外暴露；core 的 `index.ts` 只导出外部实际消费的符号——value 导出包括 `createProject`、`resolveProjectPath`、`assertInsideProject`、`isPathInside`、`categorizePath`、`serverAccessPolicy`、`shouldSkipDirEntry`、`getSupportedProviders`、`getImageSupportedProviders`，类型导出包括 `ProjectRuntime`、`ProjectManager`、`SessionRuntime`、`TriggerManager`、`TimerService`、`Logger`、`PathCategory`、`AccessPolicy`、`Decision` 等。Server 无法直接访问 store 实例
- **Store 树状结构**：store 按「聚合根 → per-agent 子 store」的树状结构组织——`ProjectStore` 作为聚合根持有 `ProjectConfigStore`、`SkillStore` 和 `Map<agentId, AgentStore>`；每个 `AgentStore` 聚合 per-agent 的 `AgentProfileStore`、`SessionStore`、`TriggerStore`、lazy 初始化的 agent-level `SkillStore`（指向 `{agentDir}/skills`）与 lazy 初始化的 `McpConfigStore`（读写 `{agentDir}/mcp.json`）。store 在构造时就确定自己的文件路径，运行时不做 agentId → 目录的查找
- **Store 只管存储**：store 是对存储层读写的抽象，不持有运行时状态（如活跃的 pi-agent-core Agent 实例）
- **thin aggregator**：聚合根（`ProjectStore`、`AgentStore`）只持有子 store 并暴露 getter（`projectStore.config`、`agentStore.sessions`），不逐个 wrap 子 store 的方法
- **结构化日志**：core 使用 pino 记录结构化日志，采用共享单实例注入模型——core 作为 library 只定义 `Logger` 类型和内部兜底工厂 `createSilentLogger`，实际的生产 logger 由 server composition root（`createServerLogger`）创建并通过 `createProject` 注入。SessionRuntime 在 `sendMessage` 中通过 `logAgentEvent` 记录 agent loop 全生命周期事件（agent_start/turn_start/tool_execution 等），stores 在关键操作（init/create/persist）中输出日志
- **AgentProfile**：业务层 agent 概念，从 `.spherse/agents/{agent-slug}/profile.md` 解析而来，包含不可变 `id`（UUID）、`createdAt`（创建时间）和 `slug`（目录名）
- **Agent context**：agent profile 的 `context` 字段声明项目内相对路径，SessionRuntime 构建 system prompt 时读取这些文件并注入 `Pre-loaded Context`
- **AgentProfileStore**：per-agent，首次读取无 `id` 的 profile.md 时自动生成并回写 `id`，创建 agent 时自动写入 `createdAt` 且更新时保持不变；支持 `getRawContent()` 获取原始 Markdown 内容用于编辑；`AgentStore.saveProfile()` 在写盘后同步刷新内存缓存的 `_profile`，避免后续 `getProfile()` 返回编辑前的旧数据（直接调底层 store 的 `save()` 只写盘不刷新缓存）
- **工具分配**：agent profile 未声明 `tools` 时默认不分配任何工具（空列表）；前端新建 agent 时通过模板默认勾选全部工具
- **工具集合**：默认工具由 `createToolsForProject(ctx: ToolContext)` 组装，包括文件读写、字符串替换编辑、文件列表、内容搜索、文件移动与复制、changelog 追加、skill 加载、HTML card 渲染、图片生成和 trigger event 触发（`emit_trigger_event`，仅当 `ToolContext.triggerManager` 存在时注册）。此外还有三个「高级 / 危险」工具经 `withApproval` 包装注册：`run_command`（shell 命令执行，unix `sh -c` / Windows PowerShell 回退链 `pwsh.exe → powershell.exe`）、`manage_agent`（agent 元数据 list/get/create/update）与 `manage_trigger`（触发器 list/create/update/delete，仅当 `triggerManager` 存在时注册）。`withApproval` 接受可选的 `shouldApprove(params)` 谓词，`manage_agent` / `manage_trigger` 据此只对写 action 请求用户确认，只读的 `list`/`get` 直接执行。`manage_agent` 不支持删除 agent（删除仍须用户在 UI 操作），且 agent id（`crypto.randomUUID()`）与磁盘目录名均由 core 生成、LLM 无法指定——目录名经 `deriveAgentSlugBase`（规范化 name，保留 CJK）+ `buildAgentDirName`（`{slugBase}-{shortId}`，碰撞时逐步加长 id 片段再退化为数字后缀）产生，`update` 永不改动已有 id 与 slug。`ToolContext` 收窄了 ProjectStore 的可用接口（`root`、`store`、`skill`、`agentSkill`、`appendChangelog`、`mutex`、`llmPolicy`、`triggerManager`、`approvalGate`、`agentId`/`agentSlug`）；`append_changelog` 复用 `ProjectStore.appendChangelog()`，`load_skill` 复用 `ProjectStore.skill`（SkillStore）+ 可选的 agent-level `SkillStore`（agent-level 优先解析），`emit_trigger_event` 复用 `TriggerManager.onUserEvent()`，不重复实现触发逻辑。除这些静态工具外，agent 还可在运行时合并 MCP 连接器提供的工具——首次 `sendMessage` 时由 `McpConnectionManager.load` 按 agent 连接所有 enabled 的 MCP server（连接按 agent 缓存、跨会话共享），将发现的工具以 `mcp__{server}_{shortid}__{tool}` 命名追加进 `agent.state.tools`。连接时还按 server capability 消费 instructions / resources / prompts：server 的 `instructions`（initialize 握手返回）连同可用 resources（含 resource templates）和 prompts 目录序列化为 `<mcp-context>` context block 注入 system prompt；声明了 `resources` capability 的 server 额外创建 `read_resource` 工具（agent 按 URI 读取资源内容），声明了 `prompts` capability 的 server 额外创建 `get_prompt` 工具（agent 按名称获取 prompt 模板）。两者均在 `ensureMcpTools` 中完成（推理前生效）。未声明对应 capability 的 server 不会创建对应工具、不拉取对应数据
- **运行时控制请求（control request）**：`SessionControlBus`（`packages/core/src/session/control-bus.ts`）提供 session 执行中途 core 向 renderer 请求并等待响应的通用机制——以 `requestId` 为 correlation key、`kind` 判别请求类型（当前仅 `"approval"`，未来可扩展 steering / 参数询问等）。`run_command` 的逐次人工确认即首个 kind：`withApproval` 包装器在 `execute` 前经 `ApprovalGate`（bus 上的薄适配器）发起请求，bus 经 `LiveSession.sendMessage` 的 `eventSink` 发 `control_request` 事件，renderer 按工具选择卡片——`run_command` 用 CommandCard 内联展示命令，其余需审批工具（`manage_agent` / `manage_trigger`）用通用 ApprovalCard 展示工具名与调用参数——两者均提供 Approve/Reject，用户决策经 chat WS 的 `resolve_control_request` 回传，`LiveSession.resolveControlRequest` → `bus.resolve` 唤醒等待中的 execute。审批等待超时 5min 自动拒绝；`abort()` 调 `bus.rejectAll` 全部失败。事件经现有 `AgentEventHandler`（已扩展为 `AgentEvent | SessionControlEvent`）与 chat WS 透传，server 不解释 `kind`
- **run_command 安全模型**：进程以用户完整系统权限运行、**无 OS 级沙箱**（路径沙箱 `resolveProjectPath`/`llmAccessPolicy` 仅约束文件类工具，对子进程的文件/网络访问无效）。唯一硬屏障是 CommandCard 内联逐次人工确认（Approve 为 destructive 配色需刻意点、无关闭路径只能显式二选一或超时拒绝）；辅以 per-agent opt-in（默认关闭、agent 配置中作为「高级/危险」折叠分组）、cwd 锁项目根、stdout/stderr 截断 100KB、超时（默认 60s，上限 600s）自动 kill 进程树、AbortSignal 随 session 中断杀进程。OS 沙箱（macOS seatbelt / Windows AppContainer）经评估永久放弃——deprecated API、SBPL/AppContainer profile 调优是无底洞、Windows 需 native addon 且跨平台安全强度不一致
- **路径安全与访问策略**：项目内路径通过 `utils/path-safety.ts` 的 `resolveProjectPath` / `isPathInside` / `assertInsideProject` 校验穿越边界。`access/path-category.ts` 的 `categorizePath()` 将项目内路径语义分类为 `PathCategory`（userFiles、rootIndex、changelog、projectConfig、projectTheme、generatedImages、attachments、skills、agentsRoot、agentProfile、agentTheme、agentMcp、agentSessions、agentSkills、agentTriggers、agentTriggerLogs、spherseMetaDir、spherseOther），路径模式定义在 `PATH_PATTERNS` 常量中，是文件分类的唯一真相。`access/access-policy.ts` 提供两个策略工厂：`llmAccessPolicy(rootPath, deniedPaths)` 用于 AI 工具（读写均经策略校验），`serverAccessPolicy(rootPath)` 用于 server 通用路由。策略内部依次完成穿越校验 → deniedPath 校验（仅 LLM）→ category 白名单校验。策略方法 `assertRead`/`assertWrite` 在拒绝时抛 `AccessDeniedError`，`canRead`/`canWrite` 返回 boolean
- **写入互斥**：`write_file`、`edit_file`、`append_changelog`、`move_file`、`copy_file` 共享 `FileWriteMutex`，避免同一文件并发写导致内容丢失；`generate_image` 写入唯一时间戳文件名（`.spherse/generated-images/{utc}-{hex}.{ext}`），无同路径并发，不使用 mutex
- **删除 agent**：compound operation，由 `ProjectRuntime.deleteAgent` 协调——SessionRuntime.evictAgent 清理活跃 session、SessionRuntime.invalidateMcpCache 关闭该 agent 的 MCP 连接缓存、ProjectManager.deleteAgent 删除数据（含磁盘上的 trigger 配置，TriggerManager 以磁盘为真相源无需单独清理内存状态）
- **Agent 配置热重载**：用户编辑 agent profile 后（经 `ProjectRuntime.updateAgent` → `ProjectManager.updateAgent`），`ProjectStore` 发出 `agent_updated` 事件。`SessionManager` 构造时订阅该事件，对所有属于该 agent 的活跃 `LiveSession` 调用 `markReloadPending()`（设 `pendingReload` 标记）。下次 `sendMessage` 时检测到 pending 标记，先执行 `applyReload()`——从磁盘重新读取 profile，重建 systemPrompt + tools + streamFn（含 timePerception 包装），并重置 `mcpMerged = false` 使 MCP 工具在本次 `ensureMcpTools` 中重新发现合并——再继续正常 prompt 流程。reload 失败时保留旧配置不中断对话。进行中的响应不受影响，配置在下一轮用户消息时才生效
- **附件处理（Attachment）**：通用 `AttachmentProcessor` 抽象（`core/src/attachments/`）在发送 LLM 前将附件 preprocess 为 content blocks（图片为首个实现：从磁盘路径读取 base64 ImageContent）。`LiveSession.sendMessage` 接收可选 `Attachment[]`，经 `prepareAttachmentUserMessage` 组装为多模态 user message 后调用 `agent.prompt()`。base64 仅在本轮 LLM 调用瞬间存在——所有 `AgentEvent` 经 `sanitizeAttachmentEvent` 将引用了 full user message 的事件中的 base64 剥离为纯文本 + `_attachments` 路径引用（覆盖 message_start/end/update/turn_end/agent_end）；`finally` 块中将 agent 内存中的 full message 替换为 stripped 版本，确保轮后内存不含 base64。附件文件落盘于 `.spherse/attachments/`（经 `attachments` category 纳入 LLM/server 读白名单，但不可写——上传走专用 `POST /attachments` 路由）
- **Skill 系统**：skill 分三层——builtin skill（来自 `@spherse/presets` 的 `PRESET_SKILL_SOURCES`，内存只读，随 app 升级更新）、project skill（`.spherse/skills/*/SKILL.md`，磁盘读写，用户自建）和 agent-level skill（`.spherse/agents/{slug}/skills/*/SKILL.md`，per-agent 私有 skill，由 `AgentStore` 的 lazy `SkillStore` 管理，无 builtin 来源）。三者均为 YAML frontmatter + Markdown body。SessionRuntime 在构建 system prompt 时合并三层 skill catalog，按 name 去重，优先级 agent-level > project > builtin（agent-level 覆盖同名 project，project 覆盖同名 builtin）；`load_skill` 工具按同一优先级解析（agent-level 先于 project/builtin 全局 store）。`SkillDefinition` 的 `source` 字段（`builtin` 或 `project`）标识来源（agent-level skill 由指向 agent 目录的 SkillStore 解析，`source` 为 `project`）。project/agent-level skill 目录可携带 `SKILL.md` 之外的附加文件（references/*、scripts/* 等），`SkillStore` 递归枚举填入 `SkillDefinition.files`，`load_skill` 加载时输出文件清单供 agent 用 `read_file` 读取（agent-level skill 的 companion files 经 `agentSkills` 路径分类纳入 LLM 读白名单）。`SkillStore` 同时拥有 skill 的写逻辑——`createSkill(name, description, instructions)` 创建目录 + 写合法 frontmatter 的 `SKILL.md`（经 `FileWriteMutex` 串行化，名称/冲突校验），`installSkill(zipPath)` 从 zip 包原子化安装（adm-zip 解析、单一顶层目录 + `SKILL.md` + frontmatter 合法 + `name===folder` 校验、逐条 zip-slip 防护、临时目录解压后移动、冲突报错不覆盖）；`ProjectManager.createSkill/installSkill` 为纯委托（与 `listSkills`/`getSkill` 一致，PM 保持 facade）。写冲突时抛 `ConflictError`，server 错误处理器映射为 409
- **触发器系统**：`TriggerManager` 管理 trigger 配置读取与触发执行，`TimerService` 负责定时轮询。`TimerService` 使用单个 `setTimeout` 链式轮询，间隔为 10 分钟，首次轮询对齐到最近的 10 分钟整数倍时间，每次 tick 调用 `triggerManager.onTimeTick()`。`TriggerManager` 以磁盘为唯一真相源（不在内存注册 trigger 条目），每次 `onTimeTick()` / `onUserEvent()` 从磁盘读取各 agent 的 `triggers/index.yml`。Trigger 分两种类型：`time`（cron 表达式定时触发）和 `event`（用户事件触发）。event 类型有两个发送端：客户端通过 `emit-trigger-event` 消息经 ws-bus 调用 `triggerManager.onUserEvent(eventName, payload)`（含 UI SDK `emitAgentTriggerEvent` action），以及 agent 通过 LLM tool `emit_trigger_event` 在对话中直接 in-core 调用 `onUserEvent`（不经 ws-bus / server contract）。`payload` 为字符串，通过 `{{payload}}` 模板变量注入消息；`sp:` 前缀为内部事件保留（如 `sp:time-tick`），UI SDK 与 LLM tool 均不可发出。`emit_trigger_event` 需 agent profile `tools` 显式启用。
- **AI 文件访问限制**：项目配置可声明 `aiAccess.deniedPaths`，同时禁止 AI 读取和写入这些路径。`llmAccessPolicy` 基于 category 白名单控制 AI 工具的读写范围——LLM 写白名单为 `userFiles` + `projectTheme` + `skills` + `agentTheme` + `agentSkills`，使 AI 可经通用工具（write_file/edit_file/move_file/copy_file）直接创建/修改 project-level（`.spherse/skills/**`）与 agent-level（`.spherse/agents/*/skills/**`）skill，AI 不可覆写 `.spherse` 下的其它 engine 数据、`AGENTS.md` 或 `CHANGELOG.md`（专用工具 `append_changelog`/`generate_image` 各自有 scoped 逻辑）；LLM 读白名单为显式列出的分类（含 `attachments` 供 agent 读取已上传的附件路径引用），`.spherse/` 下未分类的 catch-all（`spherseOther`，含 SQLite 边车文件 `sessions.db-wal`/`-shm` 等）default-deny，避免内部数据经 `search_content`/`read_file` 泄漏；`list_files`/`search_content` 递归时用 `shouldSkipDirEntry` 统一跳过 dotfile、`node_modules`、`.git`
- **项目欢迎页设置**：项目配置可声明 `welcomePage.path`，保存项目根目录内 HTML 或图片相对路径；该设置仅供 renderer 欢迎页展示使用，不注入 agent prompt，也不影响 AI 工具访问策略
- **预置内容注入**：`createProject` 检测到新项目时调用 `initPresets()`，根据 `PRESET_AGENTS` 配置自动创建预置 agent 并创建空的 `.spherse/skills/` 目录（供用户自建 project-local skill）。当前 `PRESET_AGENTS` 为空，不创建任何预置 agent。builtin skill 不再注入到磁盘，而是由 `SkillStore` 在运行时从 `PRESET_SKILL_SOURCES` 内存合并（随 app 升级更新）。预置配置来源为 `packages/presets/presets.json`。预置 agent 仅在首次创建时注入，已有项目不受影响；注入后的 agent 属于用户所有，app 升级不会覆盖

## Server 层

- **单 Fastify 实例**：整个应用只启动一个 Fastify 实例承载所有项目，由 `createMultiProjectServer()` 创建；不再为每个项目创建独立 server
- **ProjectRegistry**：`registry.ts` 维护 `Map<projectId, ProjectContext>`，项目打开时 `register()`、关闭时 `remove()`；`ProjectContext` = `{ runtime, projectManager, sessionRuntime, triggerManager, projectId }`
- **projectId**：由 core 的 `ProjectConfigStore` 在 `.spherse/project.yaml` 中生成（8 位 nanoid），跨重启和路径变化稳定；复制目录导致 id 冲突时 registry 静默改写副本的 project.yaml
- **路由按业务域拆分**到 `routes/` 目录，由 `routes/index.ts` 聚合注册；所有项目级路由统一使用 `/api/projects/:projectId/...` 前缀，`preHandler` 钩子从 registry 解析 projectId 并注入 `req.projectCtx`；全局端点（如 `/api/settings/providers`、`/api/settings/image-providers`）不带 projectId
- **API contract**：HTTP request/response 与 WebSocket message/event 的运行时 schema 定义在 `contracts/`，通过 `@spherse/server/contracts` 子入口导出给 server routes、WebSocket handler 和 renderer API client 复用；边界 JSON 进入业务逻辑前必须先通过 contract helper 解析；chat WebSocket 的 `ChatServerEvent` 是严格的 pi-agent lifecycle 事件 union（agent_start/turn_start/message_start/message_update/message_end/turn_end/agent_end/tool_execution/error 等）外加 session 级控制事件（`control_request`/`control_resolved`，带 `kind` 判别，由 `SessionControlBus` 产生而非 pi-agent-core），renderer 的 chat event 类型直接复用该 contract；client→server 方向除 `message`/`abort`/`ping` 外还有 `resolve_control_request`（回传审批决策）与 `retry`（重试上一个失败的助手回复轮次）
- **运行时 schema**：有 body 的 HTTP route 通过 server contract 中的 TypeBox schema 绑定 Fastify `schema.body` / `schema.response`；所有 JSON route（GET 含）均绑定 `schema.response`，含 pi-agent 复杂嵌套对象（session messages、turn context）的端点改用 handler 内 `parseContract` 校验以避免 fast-json-stringify 误丢字段；contract 按业务域拆文件（`agents.ts`/`sessions.ts`/...），命名用资源+操作风格（`AgentCreateRequest`/`SessionListResponse`）；renderer 的 `api.ts` 对每个响应统一走 `parseApiResponse` 校验；WebSocket 收到的 JSON 必须通过 contract parser 校验，非法消息返回统一 error event
- **内容 API**：`content.ts` 负责目录列表、文件读取、保存、删除、新建文件和新建目录；所有文件路径都通过 `serverAccessPolicy` 校验穿越边界与 category 白名单——GET 走 `.assertRead()`，POST/PUT/DELETE 走 `.assertWrite()`；server read 白名单为 `userFiles` + `rootIndex` + `changelog` + `projectTheme` + `generatedImages` + `attachments` + `skills` + `agentTheme` + `agentSkills`，server write 白名单为 `userFiles` + `rootIndex` + `changelog` + `projectTheme` + `skills`。文件读取时通过 `isBinaryBuffer`（前 8KB 采样 null-byte 嗅探）检测二进制文件，二进制文件返回 `binary:true` + 空 content（不再以 UTF-8 强解出乱码，也不把大文件整块读进内存），前端 Content Browser 据此渲染占位卡（`UnsupportedFileCard`）。`skills` 类别（`.spherse/skills/**`）经 server 读写放行，使项目技能面板可复用通用 content API 浏览/编辑技能文件；技能文件夹级生命周期（创建/安装 zip）由专用 `POST /skills`、`POST /skills/install` 路由委派 `ProjectManager`/`SkillStore` 处理（`ConflictError`→409、`ValidationError`→400）
- **文件树 API**：`file-tree.ts` 返回面向 UI 选择的项目文件列表，通过 `utils/fs-walk.ts` 的 `shouldSkipDirEntry` 过滤 dotfile/dotdir、`node_modules`、`.git`（含 `.spherse`）
- **预览 API**：`preview.ts` 为本地 HTML 与图片内容提供预览 URL，renderer 通过 iframe、图片或 HTML card 使用
- **WebSocket**：`ws-chat.ts` 推送 agent 对话事件（`/ws/projects/:projectId/chat/:agentId/:sessionId`，双向、session-scoped）；连接建立时 `restoreSession` 若因致命错误（agent/session 不存在等 `NotFoundError`）失败，以语义化 close code（`CHAT_CLOSE_CODES.SESSION_UNRECOVERABLE = 4401`，定义于 `contracts/websocket.ts`）关闭，前端据此阻断重连；瞬时错误以 `1000` 关闭触发前端重连。`sendMessage` 路径的错误不关闭连接，转为 error 事件（携带结构化 `code: ErrorEventCode`，如 `MODEL_NOT_CONFIGURED` / `PERMANENT` / `TRANSIENT`，由 `classify-run-error.ts` 按错误类型/status 判定）发回前端，前端按 code 做 i18n 渲染与重试决策；`ws-bus.ts` 是全局多路复用 bus（`/ws/bus`），将 trigger 事件、agent 元数据变更（`agent` 通道，`agent_updated` 事件，由 `ProjectStore` 在 agent 创建/更新/删除时发出，经 `ProjectManager.onAgentChange` 订阅）、fs-watch 文件变更、debug 日志四条 server→client 推送通道合并到单一连接上，客户端通过 `subscribe`/`unsubscribe` 消息按 `(projectId, channel)` 动态订阅子通道；`fs-watcher.ts` 提供按项目引用计数的共享 `fs.watch`（多订阅者共享 1 个 OS watcher），其过滤决策基于 core 的 `categorizePath` 的 watched-category 集合（`userFiles`/`rootIndex`/`changelog`/`projectTheme`/`agentTheme`/`skills`），并对 `node_modules`/`.git` 任意路径段降噪；项目技能面板的技能树刷新与 Files 面板一致，统一走该 fs-watch 通道（不使用主动 refreshKey）；bus envelope 与各通道事件 type/payload 的运行时 schema 统一定义在 `contracts/bus.ts`
- **触发器 API**：`trigger.ts` 提供触发器 CRUD 和手动触发（`/triggers` 增删改查、`/trigger-logs` 运行日志、`/run` 手动触发）
- **图片导出 API**：`images.ts` 提供 `POST /api/projects/:projectId/images/export`，将 `.spherse/generated-images/` 下生成的图片复制到用户选择的项目内目标路径；src 和 dest 均通过 `serverAccessPolicy` 校验穿越边界与 category 白名单
- **项目 settings API**：`settings.ts` 暴露 `/api/projects/:projectId/settings/ai-access` 读写项目级 AI 读取禁止列表，暴露 `/api/projects/:projectId/settings/welcome-page` 读写项目级欢迎页路径；`settings.ts` 还暴露 `/api/projects/:projectId/settings/theme` 读写项目级主题 CSS（GET 返回 `{ ok, content }`，文件不存在时 content 为空串；PUT body `{ content }` 原样落盘，返回 `{ ok }`）；`settings.ts` 同时承载全局 provider 列表端点（文本 `GET /api/settings/providers`、图片 `GET /api/settings/image-providers`）；renderer 不直接通过 content API 编辑 `.spherse/project.yaml`
- **MCP 连接器 API**：`agent-mcp.ts` 暴露 `GET/PUT /api/projects/:projectId/agents/:id/mcp`。GET 委派 `ProjectManager.getAgentMcp`（经 `McpConfigStore.getConfig` 读 `mcp.json`），PUT 委派 `ProjectRuntime.updateAgentMcp`（保存后调用 `SessionRuntime.invalidateMcpCache` 使该 agent 的连接缓存失效）。contract schema（`mcpServerConfig` 判别联合、`agentMcpResponse`、`agentMcpUpdateRequest`）定义在 `contracts/agents.ts`

## Electron 层

- **环境隔离**：`electron/bootstrap.ts` 作为构建入口，dev 模式（`app.isPackaged === false`）下将 `userData` 重定向到 `Spherse-Dev/` 目录，使 dev 和 prod 的 electron-store、localStorage 等所有数据完全隔离，可同时运行；`NODE_ENV=test` 时保留测试启动参数指定的 `userData`，确保 E2E 用例隔离
- **IPC handler** 集中在 `electron/ipc/` 目录，按业务域拆分为 project、settings、updater、debug、skill
- **preload** 是安全桥梁，声明 Renderer 可用的 IPC 方法白名单
- **项目 server 管理**：单一 Fastify 实例在 `app.whenReady()` 时通过 `ensureServer()` 启动一次，项目打开/关闭只操作 `ProjectRegistry`（register/remove），不再 create/close Fastify；`electron/server.ts` 暴露 `ensureServer`、`registerProject`、`unregisterProject`、`getServerPort`、`stopServer`
- **设置持久化**：`electron/settings.ts` 使用 electron-store 保存打开项目、最后活跃项目和 `AppSettings`（统一 schema：`locale` + `models: { text: ModelGroupSettings, image: ModelGroupSettings }` + 可选 `customProviders: CustomProviderDef[]`（用户自定义 OpenAI 兼容供应商定义，无密钥；仅文本 tab）+ 可选 `debugToolsEnabled`（控制 Debug Tools 入口可见性）+ 可选 `theme`（`"light"` | `"dark"` | `"system"`，默认 `"system"`，由「设置 > 通用 > 外观」切换），每个 group 含 `defaultModel`、per-provider `apiKey`，文本 group 另含可选 `sampling: SamplingParams`（`{ temperature?: number; topP?: number }`，未设字段代表「恢复 provider 默认」））。保存设置后同步到进程环境变量：文本 provider key 按 `PROVIDER_ENV_KEYS` 映射（如 `OPENAI_API_KEY`），图片配置写入 `SPHERSE_IMAGE_MODEL`（`"provider/modelId"` 格式）和 `SPHERSE_IMAGE_API_KEY`；API key 输入框显示掩码（前 4 后 4），保存时空串跳过、含 `****` 保留旧值。自定义供应商不走 env，而是由 `applySettingsToEnv` 末尾调用 core 的 `syncCustomProviders(defs, apiKeys)`（启动时 `restoreEnvFromSettings` → 注册在 `ensureServer` 之前；自定义 apiKey 复用同一 providers map 的 mask/merge），其 auth 用闭包直取 apiKey（keyless 本地服务器返回占位 key）
- **外观模式切换**：用户可在「设置 > 通用 > 外观」选择浅色 / 深色 / 跟随系统（`AppSettings.theme`）。Electron main 在启动（`restoreEnvFromSettings`）与每次保存设置时调用 `nativeTheme.themeSource = theme`，renderer 侧的 `@media (prefers-color-scheme: dark)` 与 Tailwind `dark:` 工具类据此生效——因此 CSS 变量、项目级 `.spherse/theme.css`、agent 聊天主题中现有的 `@media (prefers-color-scheme: dark)` 规则全部自动跟随应用选择的外观模式，无需额外改造
- **Provider catalog**：`core/model-providers/index.ts` 从 pi-ai `builtinModels()` / `builtinImagesModels()`（`@earendil-works/pi-ai/providers/all`）实例化的 module 级 **Mutable** 单例 `models` / `imagesModels` 动态生成 provider catalog——文本 catalog 由 `getSupportedProviders()` 经 `ENABLED_PROVIDERS` 过滤内置 provider（14 个 provider：openai/anthropic/google/deepseek/zai(Zhipu)/minimax/minimax-cn/xiaomi/moonshotai/moonshotai-cn/xai/openrouter/kimi-coding(Kimi For Coding)/opencode-go），图片 catalog 由 `getImageSupportedProviders()` 聚合所有已注册图片 provider（OpenRouter 内置 + 智谱）。智谱图片 provider 通过 `createZhipuImagesProvider()`（`model-providers/zhipu-images.ts`）以 `createImagesProvider()` 工厂构建，模块加载时 `setProvider` 注入 `imagesModels`。`PROVIDER_ENV_KEYS` 映射文本 provider→env key，`IMAGE_PROVIDER_ENV_KEYS` 映射图片 provider→`SPHERSE_IMAGE_API_KEY`。用户自定义 OpenAI 兼容供应商通过 `syncCustomProviders(defs, apiKeys)` 在运行时以 `createProvider()` + `MutableModels.setProvider()` 注入 `models` 单例（id 带 `custom-` 前缀避免与内置冲突），其 `getSupportedProviders()` 段在内置循环之后追加并标记 `custom/keyless/baseUrl`；内置 provider 仍 env-var 驱动不受影响
- **模型解析与默认模型切换**：模型 id 由 `resolveEffectiveModelId(profile, globalDefaultModel)` 解析（`profile.model || globalDefaultModel || undefined`，用 `||` 而非 `??` 使空串视为未配置）。模型解析延迟到 `sendMessage`：`buildAgent` 在无模型时构造一个不携带 model 的 Agent（`initialState.model` 可选），session 可在无模型状态下打开存活；`sendMessage` 前由 `ensureModelForAgent` 守卫，无模型或不可解析时抛 `ModelNotConfiguredError`（被 `ws-chat.ts` 的 catch 转为 `{type:"error", code:"MODEL_NOT_CONFIGURED"}` error 事件发回前端，连接不关闭）。SessionRuntime 暴露 `setDefaultModel()` 方法，IPC save-settings 后通过 `electron/server.ts` 的 `updateDefaultModel()` 同步更新运行时的 `globalDefaultModel`（仅文本模型注入运行时；图片模型经 env 注入，`generate_image` tool 从 `process.env` 直读，不经运行时）。对活跃会话即时生效：setter 遍历 `activeSessions` 重新解析并热替换 `agent.state.model`（下一轮生效，进行中的响应不受打扰）；profile 显式指定 `model` 的 agent 不受全局默认变更影响。模型未配置时 setter 跳过该 agent（不抛错），待用户配置后自动同步
- **模型采样参数（SamplingParams）**：采样参数（temperature、top_p）是与 `defaultModel` 同级的全局默认，统一收进 `AppSettings.models.text.sampling: SamplingParams`（`{ temperature?: number; topP?: number }`，每个字段可选，未设代表「恢复 provider 默认」）。传播链路：IPC `save-settings` handler **无条件**调用 `electron/server.ts` 的 `updateSampling()`（与 `updateDefaultModel()` 的 `if (defaultModel)` 守卫不同，因为 undefined 即「恢复 provider 默认」语义需要传播）→ `ProjectRegistry.setSampling()` → 各 project 的 `SessionManager.setSampling()`；registry 同时缓存当前 sampling，后续 `register()` 的新项目在 `createProject` 时传入。注入点：`SessionManager.buildAgent()` 调用 `getChatStreamFn(ctx.sampling)`，后者按字段分发：`temperature` 是 pi-ai typed `StreamOptions` 字段，直接注入 options；`topP` 因 pi-ai 无 typed 字段且 `buildBaseOptions` 是 allowlist 会丢弃未知 key，改用 `onPayload` 回调按 `model.api` 分支注入（`openai-completions`/`openai-responses`/`anthropic-messages` → 根级 `top_p`；`google-generative-ai` → `config.topP`；未知 api → no-op）。对活跃会话即时生效：`setSampling` 遍历 `sessions` 重赋每个 agent 的 `agent.streamFn = getChatStreamFn(ctx.sampling)`（下一轮生效）；仅文本路径生效，图片走 env 不涉及采样参数；`ModelGroupSettings.sampling` 经 `mergeModelGroup` / `maskModelGroup` 透传（incoming 覆盖 prev，undefined 即清除），否则会被 API key 掩码逻辑丢弃
- **时间感知（Time Perception）**：agent profile 的 `timePerception` 配置（per-agent）启用后，Agent 在对话中看到的时间线可与真实世界不同步。感知时间由纯函数 `perceivedMs = startMs + (realMs - epochMs) × flowRate` 从每条消息的真实时间戳推导。注入点在模块级函数 `composeStreamFn(sampling, timePerception)`：对 base streamFn（`getChatStreamFn`）可选地包装 `wrapWithTimePerception`，在调用 LLM 前对 context.messages 中每条 **user** 消息注入 `<time>感知时间</time>` XML 标签前缀（运行时计算，不修改 `agent.state.messages`，不持久化）。`buildAgent` 和 `applySampling` 统一调用 `composeStreamFn`，确保构建和热更新一致。只注入 user 消息以避免 LLM 从 assistant 历史中模仿输出时间标签；system prompt 的 `<session-context>` 注入 `time-perception: enabled` 标记及"Do not output `<time>` tags"指令。Trigger 系统、存储时间戳、日志全部保持真实墙钟——感知时间仅影响 LLM 看到的消息内容
- **图片生成配置**：图片模型与 API Key 存于全局 `AppSettings.models.image`，经 env 注入（`SPHERSE_IMAGE_MODEL` / `SPHERSE_IMAGE_API_KEY`），core `generate_image` tool 从 `process.env` 直读并通过 `getImagesModels().getModel(provider, modelId)` 统一解析模型（OpenRouter / 智谱走同一 `imagesModels` 单例），不经 `ToolContext` getter；「是否启用」隐式判断（provider + model + key 三者齐）
- **开发调试**：debug IPC 暴露 DevTools、electron-store 查看、reload renderer、reset app data 等动作；Debug Tools 入口（activity bar 的 Bug 图标）默认仅在开发模式（`!app.isPackaged`）可见，生产用户可在「设置 > 通用」开启 `AppSettings.debugToolsEnabled` 后显示（门控为 `isDev || debugToolsEnabled`）。Debug Tools 包含 Streaming Log 面板（可拖动悬浮窗口，通过 `/ws/debug` WebSocket 实时显示 server 日志）和 Turn Context 下载（通过 `GET /api/debug/sessions/:id/turn-context` 导出当前 session 的 system prompt + messages + tools 为 JSON 文件，便于排查 agent 行为）
- **App 更新机制**：`electron/updater.ts` 封装 `electron-updater`，通过 GitHub Releases 分发更新。`autoDownload` 和 `autoInstallOnAppQuit` 均关闭，全程需要用户主动同意（同意下载 → 下载完成确认重启）。启动后延迟 5s 静默检查（`main.ts`），静默检查的 `update-not-available`/`update-error` 事件被 `silent` 标记抑制不推给 renderer，仅 `update-available` 弹窗。平台差异：Windows 走完整 electron-updater 流程（check → download via CancellationToken → quitAndInstall），macOS 未签名阶段走通知模式（GitHub Releases API 版本比较 + release notes 展示 + `openExternal` 跳转下载页，不下载安装）。`checkForUpdates` 在 dev 模式（`!app.isPackaged`）直接返回 upToDate。IPC 契约以事件流为唯一真相源：`invoke` 只触发动作返回 void，`webContents.send` 推送 5 个事件（`update-available`/`update-not-available`/`download-progress`/`update-downloaded`/`update-error`），preload `onUpdateEvent` 注册监听并返回 unsubscribe 函数。renderer 侧 `useUpdateChecker` hook 用 `useReducer` 管理状态机（idle/checking/upToDate/available/downloading/downloaded/error），`errorPhase` 区分检查失败与下载失败。CI（`.github/workflows/build-and-release.yml`）由 git tag 触发，`create-release` job 先行创建 Release，mac/win 并行构建，win `--publish always` 上传 `latest.yml` + `.exe`（electron-updater 读），mac `--publish never` + `gh release upload` 仅上传 `.dmg` 供手动下载（不发 `latest-mac.yml`）

## 前端路由与状态

- **Hash Router**：renderer 使用 React Router Hash Router，路由表达应用内导航状态，避免 Electron 本地页面刷新时依赖服务端 history fallback
- **项目路由**：项目、会话和内容页通过 URL 表达，当前路径形态为 `/project/:projectId`、`/project/:projectId/chat/:sessionId`、`/project/:projectId/content?path=...`
- **projectId**：URL 中使用 `.spherse/project.yaml` 中的稳定 id（nanoid 8 位 token）作为路由参数，替代旧的基于目录名生成的 projectKey；全链路（core → server → IPC → renderer 路由 → localStorage key）统一使用 projectId 作为唯一身份标识
- **项目内 lastRoute**：每个打开项目的子页面路由持久化在 renderer localStorage（`spherse:last-route:<projectId>`），不写入 electron-store。应用启动、项目切换和关闭当前项目后的下一个项目导航都会恢复该项目的 lastRoute；关闭项目时清理对应的 localStorage key
- **应用级 store**：`app-store.ts` 管理打开项目集合、当前项目、restore/open/close/reveal 等 Electron IPC 相关动作，并持久化左侧 side panel 固定/自动收起偏好
- **项目数据 store**：`project-data-store.ts` 按 projectId 缓存 agents、sessions、初始消息、streaming 状态、各 agent 是否存在启用触发器的派生标记（`hasEnabledTriggersByAgent`，由 agent-trigger feature store 在 trigger CRUD chokepoint `refreshTriggers` 中同步派生，`ProjectScope` 在项目打开时为所有 agent 预加载）以及 loading/error 状态；session 列表按 agent 分页加载（每页 10 条 + `sessionPaging` 状态跟踪 hasMore/offset/loadingMore），`refreshSessions` 取首页、`loadMoreSessions` 追加下一页
- **项目 UI store**：折叠状态、浮窗会话状态等纯 UI 状态按 projectId 管理，通过 renderer localStorage 持久化。折叠状态在 `features/agent-session-list/store.ts`，浮窗会话状态在 `features/floating-chat/store.ts`，浮窗内容浏览器（多窗口，按 projectId → filePath 映射）在 `features/floating-content-browser/store.ts`。浮窗 chrome（拖拽/调整大小）由共享的 `components/floating-frame/` 提供，floating-chat 与 floating-content-browser 通过 `hookPrefix` 参数复用并各自生成 `data-chat-float-*` / `data-content-float-*` 主题钩子
- **局部状态边界**：文件编辑 dirty/conflict、弹窗表单等短生命周期状态保留在对应组件或 feature hook 内；Chat 输入框草稿按 sessionId 缓存在 renderer `localStorage`，用于 session 切换和应用重启后的草稿恢复；欢迎页设置与主题设置 dialog 的打开状态保留在 `ActivityBar` 内（通过「设置」二级菜单触发，仅 active 项目可见），设置变更通过 `lib/events.ts` 中的 renderer 自定义事件通知：欢迎页重新读取项目配置、`useCustomTheme` 重新挂载主题 `<link>` 热更新
- **Chat run / WebSocket 生命周期**：Core `LiveSession` 只拥有 agent 上下文、执行与消息持久化，继续通过单次 `sendMessage` callback 输出事件；server `ChatSessionHub` 按 project/session 建立 transport channel，独立负责共享 restore、当前 run 状态、事件广播、压缩事件快照和无 attachment 时的空闲释放。WebSocket 是 channel 的可替换 attachment，socket close 只解除 attachment；若 agent 正在运行，Core run 会继续执行并持久化消息，重连后由 hub 先重放当前 run 快照，再发送 `run_status` 对账运行状态。WebSocket 连接具备心跳保活与指数退避重连（1/2/5/10/30s）：每 30s 发 ping，只有连续 60s 等不到 pong 才关闭；renderer suspend 导致 timer 大幅跳跃时会重置探测窗口，避免恢复后误判超时。socket 发送失败被隔离在 server attachment 边界，Core 则保证 `message_end` 先持久化再回调，连接故障不能打断 agent 或阻止最终消息落库。
- **Chat streaming store / runtime 边界**：`features/chat/runtime/streaming-store.ts` 只维护 UI 可观察的 session 状态与公开 actions；每个 session 的 WebSocket、心跳、重连 timer、连接期事件缓冲和重连历史对账由同目录下非响应式 `ChatSessionRuntime` 持有，并通过 `ChatRuntimeRegistry` 管理生命周期，transport 对象不进入 Zustand。`connectionStatus` 表达 socket 的 disconnected/connecting/open，`historyStatus` 独立表达 pending/syncing/ready，因为连接状态与历史是否已经成功对账是正交维度。`useChatSession` 只负责 attach/detach 与选择状态，切换页面或关闭 chat 不会中断后台流式输出。正常断线保留 streaming 和未完成消息，只有致命连接错误或服务端 `run_status: inactive` 才结束前端运行态。WebSocket 事件按 animation frame 批量归约，避免高频 token update 触发过多 React render；`features/chat/model/chat-session-reducer.ts` 仅负责实时事件到 view state 的纯数据归约，历史解析/稳定 ID 合并位于同目录 `chat-history.ts`，实时与历史共用的 tool/card 投影位于 `chat-tool-projection.ts`；`agent_end` 时继续通过 `lib/aggregate-file-changes.ts` 聚合本次 run 的文件变更。**失败/错误重试与韧性**：错误分两条来源——Source 1（`sendMessage` 在 `agent.prompt()` 之前抛错，如 `ModelNotConfiguredError`，经 `ws-chat.ts` 的 `classify-run-error.ts` 判定 `code` 后发 `error` 事件，用户消息未落库）与 Source 2（pi-agent-core `handleRunFailure` 吞掉异常、emit 合成 `message_end`(`stopReason:"error"`)，用户消息已落库）。reducer 用 `_turnError` 标记区分：`message_end`(error) 与「`error` 事件落到 streaming 气泡」置 true（Source 2），`error` 事件新建空气泡不置（Source 1）。重试决策是纯函数 `features/chat/model/retry-plan.ts`（`planRetry` 返回 `retry-last`/`resend`/`none`，`shouldAutoRetry` 判瞬时额度），store 的 `executeRetry` 只执行 plan；Source 2 走 client→server `retry` 消息（服务端 `LiveSession.retryLastTurn` 弹出失败助手消息 + 删 DB 行 + `agent.continue()`），Source 1 / 发送失败（`_sendFailed`）走重新 `sendMessage`。瞬时错误（`code:TRANSIENT`）由 store 自动重试（backoff `[2s,5s]`，上限 2 次，`maybeAutoRetry` 用 `autoRetrying` 标记独占退避窗口、`streaming` 防 run 重入），耗尽或永久错误落错误气泡 + 手动重试按钮。韧性增强：断连横幅（`ConnectionBanner` 读 `connectionStatus`/`reconnectFailed`）、历史对账失败带退避重试 + `historyError`、重连达上限停止 + 手动重连、`onerror` 主动 close 消除僵尸 socket、`respondApproval` 返回值校验 + toast。
- **Chat 历史懒加载与对账**：聊天历史按 turn（一条 user 消息 + 其后的 agent 回复）分页，attach 与每次重连时加载最新 10 turn。core `SessionStore.getRecentTurns` 以 `beforeId` 为游标、`id < cursor` 倒序取行后按 turn 边界切片；分页 contract 返回 `{ entries: [{ id, message }], hasMore, oldestId }`，稳定 message id 同时用于历史分页游标和前端幂等合并，避免重连补拉产生重复消息；无分页参数时仍向后兼容返回全量裸消息数组。前端 `loadMore` 用 `oldestId` 加载更早 turn，重连则用最新页覆盖同 id 的缓存并保留未持久化的 optimistic user 消息。由于消息列表使用 `flex-direction: column-reverse`，load-more 前由 `useChatScroll` 捕获当前 `scrollTop`，messages 变更后在 `useLayoutEffect` 恢复同一距底部偏移，避免浏览器 anchoring 不可靠导致跳动。agent 运行时上下文恢复仍走全量消息，与显示分页互不影响。
- **Chat 自动滚动（CSS column-reverse 方案）**：消息列表容器 `MessageList` 使用 `flex-direction: column-reverse`（DOM 顺序 newest→oldest，视觉上 newest 在底部、oldest 在顶部），`scrollTop=0` 即「底部」。流式 token 到达时末条 assistant 消息在底部增长，`scrollTop` 保持 0 → **浏览器原生逐帧贴底，无需 JS 节流滚动**（取代了旧的 1s 节流 `scrollIntoView` + `stickToBottomRef` 方案）。用户向上滚动阅读历史时 `scrollTop<0`，新内容仍在底部生成，依赖 Chromium 默认 `overflow-anchor` 保持阅读视口稳定，自动跟随与阅读历史天然解耦、不再互相打架（load-more 的 prepend 路径因 `overflow-anchor` 在 `column-reverse` 下不可靠，改用上条所述的显式捕获/恢复，不依赖浏览器 anchoring）。「回到底部」FAB 显隐由单一阈值判定：`scrollTop >= -NEAR_BOTTOM_THRESHOLD(100px)` 即视为贴底（`isNearBottom`）。仅保留两处 JS 介入滚动：用户发送消息时强制 `scrollToBottom("smooth")`（`scrollTo({top:0})`）覆盖阅读状态；FAB onClick 同样调用 `scrollToBottom("smooth")`（不透传 React 点击事件，避免其被当作 `behavior` 参数）。session 切换时按 store 中的 `scrollPosition` 恢复位置（通过 `scrollTopRef` 在卸载时持久化；column-reverse 下保存的 `scrollTop` 为距底部偏移，语义与恢复一致；该恢复与 load-more 恢复同在 `useLayoutEffect` 中执行，规避 keyed remount 下被动 effect cleanup 读取已脱离 DOM 的 `scrollTop=0` 问题）。注意：DOM 顺序为 newest→oldest，屏幕阅读器会从最新消息读起（当前为已知取舍）
- **Chat 专属类型归属**：`ChatMessage`、`ToolCallInfo`、`HtmlCard` 等 chat 内部消费的类型集中在 `features/chat/types.ts`，`lib/types.ts` 仅保留 contract re-export（`AgentProfile`、`SessionInfo` 等）与应用级类型（`ActiveSessionInfo`）；`lib/` 作为纯叶子层不反向 import feature，chat feature 类型自洽
- **页面 / layout / feature 边界**：`pages/` 只做路由适配和参数校验；跨 feature 的页面编排放在 `layouts/`；业务域专属 UI、hooks 和局部动作放在 `features/{domain}/`

hook。iframe 通过 `postMessage` 发送 `type: "spherse:action"` 消息，由 `useSpherseMessageListener` hook 接收并分发到注册的 handler；App 内代码直接调用 `dispatchAction`。外部调用经 rate limiter 限流（每分钟最多 10 次），内部调用无限制。rate limiter ## i18n

- **locale 是应用级设置**：持久化在 electron-store 的 `settings.locale`，默认 `zh-CN`
- **翻译资源**：集中管理在 `@spherse/i18n` package 的 `src/locales/{zh-CN,zh-TW,en}.ts`
- **前端消费**：renderer 通过 `@spherse/i18n/react` 的 `I18nProvider` + `useI18n()` 获取翻译
- **后端消费**：Electron/server/core 通过 `translate(locale, key, params)` 纯函数获取翻译
- **校验**：`npm run check:i18n` 检查 locale key 一致性和插值变量一致性
- **开发者 skill**：`.opencode/skills/i18n/SKILL.md` 指导 coding agent 迁移用户可见字符串

## 前端样式

- **基础组件层**：前端基础 UI 统一使用 shadcn/ui 本地源码组件，组件位于 `packages/app/src/components/ui/`，当前底层 base 为 Base UI
- **组件生成配置**：`packages/app/components.json` 记录 shadcn 样式 preset、Tailwind v4 CSS 入口和 `@/*` alias
- **单一 Token 体系**：所有 design token 统一使用 Spherse 自有命名空间（`--sp-*`），CSS 变量定义在 `styles.css` 的 `:root`，暗色模式通过 `@media (prefers-color-scheme: dark)` 覆盖。组件 Tailwind 类名（`bg-background`、`text-foreground` 等）**不动**——通过 Tailwind `@theme inline` 桥接层（`--color-background: var(--sp-background)`）解析，与源变量名解耦。不维护旧的自定义变量（`--surface`、`--base` 等已移除），旧的 shadcn 组件库前缀变量已全部更名为 `--sp-*`
- **Spherse 业务 token**：shadcn 语义未覆盖的业务语义按需新增 `--sp-{name}` 变量 + `--color-{name}` Tailwind 映射（如 `--sp-success` / `--sp-success-foreground` / `--sp-warning` / `--sp-warning-foreground` / `--sp-diff-added`），注册后业务组件可用 `text-success`、`bg-warning` 等 Tailwind 类
- **样式写法**：所有样式通过 Tailwind 工具类写在组件 className 中，不在 `styles.css` 中新增手写 CSS class。禁止硬编码颜色值（如 `text-[#333]`），需要新颜色时在 `styles.css` 中注册 CSS 变量 + Tailwind 颜色
- **语义 Token 使用**：使用 shadcn 语义 token（`bg-background`、`bg-card`、`bg-muted`、`bg-primary`、`bg-accent`、`text-foreground`、`text-muted-foreground`、`border-border`、`text-destructive` 等）。Spherse 自有业务语义按需新增 `--sp-*` token
- **间距与阴影**：使用 Tailwind 标准 scale（`p-2`、`rounded-md`、`shadow-sm` 等），不硬编码 magic number
- **暗色适配**：业务组件不写 `dark:` 修饰符，由 CSS 变量值切换自动适配。仅 shadcn/ui 组件源码中已有的 `dark:` 保留
- **Markdown 渲染**：动态 Markdown 统一通过 `MarkdownContent` 组件映射 `react-markdown` 节点样式，不在 `styles.css` 里维护 `.chat-markdown` 或 `.prose-content` 选择器
- **三级主题层叠**：主题系统形成清晰的三级层叠（低 → 高优先级）——① App defaults（`styles.css` 内置 `:root` / `--sp-*` 变量）；② Project theme（`.spherse/theme.css`，经全局 `<link>` 注入 `document.head`，可同时承担「全局 UI 变量」`--sp-*` in `:root` 与「全局 chat 默认样式」`[data-chat-root] { ... }` 两个角色）；③ Agent theme（`.spherse/agents/{agent-slug}/theme.css`，chat 容器内后载入的 `<link>`）。三级主题均以 `<link>` 从 preview 路由载入（`href` 锚定在 `/preview/*` 文件服务树内），相对 `url()` 引用的图片/字体等资源因此能正常解析到项目文件。相同特异性的规则后者胜出（agent theme 的 `<link>` 在 DOM 中位于 chat 容器内，比 project theme 的 `<link>`（`document.head`）更靠后），agent theme 自然覆盖 project theme 的 chat 规则
- **项目级自定义主题**：用户可通过项目根目录 `.spherse/theme.css` 覆盖 CSS 变量实现项目全局主题定制，只允许覆盖 `:root` 中已有的变量名。应用内可通过项目头像右键菜单「设置 → 主题」打开 CSS 编辑器直接读写该文件。前端通过 bus 的 fs-watch 通道监听 `.spherse/theme.css` 变更（无论来源是 UI 保存、外部编辑器还是 LLM 工具修改），文件变更时 `useCustomTheme` 自动热重载 `<link>` 样式表
- **Agent 聊天主题（原生 CSS nesting）**：每个 agent 可在 `.spherse/agents/{agent-slug}/theme.css` 定义聊天窗口主题，采用**原生 CSS nesting**——最外层为 `[data-chat-root] { ... }`，内部嵌套各选择器自动作用域到 chat 内。废弃了自写的 `scopeCss`（`packages/app/src/lib/scope-css.ts` 已删除），用户直接写标准 nesting 语法，浏览器原生处理 `@media` / 嵌套 / 裸声明等所有情况。前端进入聊天页时将该文件以 `<link rel="stylesheet">` 形式从 preview 路由载入到聊天窗口内（`useAgentTheme` 构造 `href` 为 `.../preview/.spherse/agents/{agent-slug}/theme.css`，相对 `url()` 解析基址为 agent 目录，因此主题引用的本地图片/字体可正常解析），优先级高于项目级主题；该样式只作用于当前 agent 的聊天窗口，不影响侧边栏等外部 UI。inline chat 与 floating chat 共用同一份 CSS（由 `Chat` 组件统一载入，`[data-chat-root]` 块同时覆盖两者，floating 的 `data-chat-root` 嵌套在 `data-chat-float-root` 内），若需单独定制浮动窗 chrome 再加一个 `[data-chat-float-root] { ... }` 顶层块
- **Chat dark mode**：聊天主题暗色适配通过在 `[data-chat-root] { ... }` 内嵌套 `@media (prefers-color-scheme: dark) { ... }` 实现，浏览器原生处理嵌套 at-rule，dark mode 自动跟随 OS 切换，且作用域天然限定在 chat 内，不污染全局
- **Chat theme 自动重载**：server 端 fs-watcher 已将 `agentTheme` 纳入 watched-category 白名单，`.spherse/agents/*/theme.css` 变更会经 bus 的 fs-watch 通道推送事件；renderer 端 `useAgentTheme` 订阅该通道，命中后 debounce 并更新 `<link>` 的缓存破坏 query，触发样式表重新拉取，无需重开窗口即可看到效果（floating chat 主题由其内部渲染的 `Chat` 组件统一负责，不再单独订阅）
- **聊天/文档主题选择器**：应用根容器（整窗最外层，铺满视口且 `position: relative`）暴露 `data-app-root`，供项目级主题用 `::before` / `::after` 或固定定位层在窗口任意位置叠加全局装饰（背景纹理、角标、水印等）；聊天窗口对用户主题暴露 `data-chat-root`、`data-chat-header`、`data-chat-messages`、`data-chat-message[data-role]`、`data-chat-bubble`（消息气泡内容容器）、`data-chat-composer`、`data-chat-composer-input`（输入框外框）、`data-chat-float-close`（浮动窗关闭按钮）等入口；Markdown 元素暴露 `data-md-code`（代码块 `<pre>`）、`data-md-code-inline`（行内 `<code>`）、`data-md-quote`（引用），chat 与 document 视图共用同一组属性（作用域由主题作者用父选择器显式表达）；文档视图容器暴露 `data-content-doc`，供项目级主题精准定制文档视图 markdown 样式；项目面板暴露 `data-project-panel`，内容浏览器暴露 `data-content-browser`，供项目级主题定制这两个区域的背景与外观；全局 toast 暴露 `data-toast-root`（包裹 sonner 的 `position: fixed` 视口容器），供项目级主题用 `[data-toast-root]` 前缀 + sonner 原生 `[data-sonner-toast]`/`[data-type]`/`[data-title]`/`[data-description]` 等后代选择器定制 toast 外观。变更这些 DOM 入口、聊天布局或新增可主题化选择器时，需要同步更新 `packages/presets/templates/agent-theme-template.css`、`packages/presets/skills/create-agent-chat-theme/SKILL.md` 与 `packages/presets/skills/create-ui-theme/SKILL.md`

- **浮窗聊天**：会话可脱离主窗口进入可拖拽/可调整大小的 CSS overlay（Portal 渲染到 `document.body`，z-index 按 side panel pinned 状态动态切换——pinned 时 `z-50` 在面板之上，unpinned 时 `z-30` 在面板之下）。同一项目最多一个浮窗，新浮窗自动关闭已有浮窗。浮窗状态（sessionId、position、size）持久化在 `project-ui-store` 并写入 renderer localStorage。浮窗会话在侧边栏显示选中态，点击无响应；关闭浮窗后会话回到未选中状态。双击浮窗标题栏可关闭浮窗并导航到该会话的完整聊天页。浮窗聊天主题复用 Agent 聊天主题，通过 `data-chat-float-root`、`data-chat-float-titlebar` 选择器限定作用域。`FloatingChatManager` 渲染在 `ProjectLayout` 内，项目切换时随 `key={projectKey}` 完整卸载重建。文本选中发起的发送至当前会话列表包含浮窗会话，浮窗会话的发送不触发导航。
