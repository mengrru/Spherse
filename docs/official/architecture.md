# 架构约定

## Package 边界

- **@spherse/core**：纯 Node.js 核心逻辑，负责项目数据、agent profile、session、skill、tool 和运行时管理，不依赖 Electron 或 Fastify
- **@spherse/presets**：内置模板与预置静态内容，构建前通过 `scripts/sync-templates.mjs` 将 `templates/*.md` 同步为可导入常量，并从 `presets.json` 及 `skills/` 目录生成预置 skill 源码、agent 配置和 prompt template（`PRESET_SKILLS`、`PRESET_AGENTS`、`PRESET_SKILL_SOURCES`、`PRESET_PROMPT_TEMPLATES`）；其中 `PRESET_SKILL_SOURCES` 由 core 的 `SkillStore` 在内存中合并为 builtin skill，`PRESET_AGENTS` 供 `initPresets()` 在新项目创建时注入，`PRESET_PROMPT_TEMPLATES` 供前端 Agent 创建对话框作为可复用 prompt 模板徽章选择（不参与项目创建注入）
- **@spherse/server**：Fastify API 层，只负责把 HTTP/WebSocket 请求转发到 core 的运行时模块（ProjectManager、SessionRuntime、TriggerManager）。`ProjectContext` 以 `runtime` 为单一真相源（`projectManager`/`sessionRuntime`/`triggerManager` 为转发 getter 糖）；model catalog 由组合根持有并注入（desktop main 创建 `appModelCatalog` 单例 → `createMultiProjectServer({ modelCatalog })` → registry → `assembleProject`，settings 变更 sync 一次全体 runtime 可见）
- **前端三层分离**：`@spherse/app`（共享 React renderer，含 features/stores/lib/components 与 `HostBridge` 接口）+ `@spherse/desktop`（Electron 桌面壳，main/preload/electron 基础设施 + 桌面专属 feature，提供 `ElectronHostBridge`）+ `@spherse/web`（移动端 PWA 壳，提供 `WebHostBridge`，经 Cloudflare Quick Tunnel 远程连接桌面 server）。renderer 通过 `HostBridge` 抽象访问宿主能力（IPC/外部链接/更新等），不直接 `window.electronAPI`，从而可在桌面与 Web 两种宿主复用。`HostBridge.capabilities: HostCapabilities` 声明各宿主的能力开关（`projectManagement`/`filePicker`/`appUpdate`/`devTools`/`mobileAccess`/`openFileExternal`/`settings.editable`/`content.editable` 等），renderer 据此条件渲染宿主专属 UI——如 Content Browser 的二进制文件占位卡「用默认应用打开」按钮仅当 `openFileExternal:true`（桌面端）显示，Web 端该能力为 `false` 不显示

## Core 层

- **微内核 + Capability 架构**：core 采用「贡献即数据、依赖即窄接口」的组合式架构；AgentRunner 对具体能力零 import（含 compaction 与 MCP）。`kernel/` 只含类型与纯组合子（零 I/O）：`Capability` 接口（id / init / tools / contextBlocks / turnHooks / streamDecorators / contextProjectors / previewTransforms / pathRules / onAgentDeleted / onAgentConfigChanged / shutdown——streamDecorators 改写出站请求流（洋葱），contextProjectors 在 convertToLlm 前投影上下文消息（管线序），previewTransforms 仅为 debug turn-context snapshot 重放 stream 级消息改写（如 time-perception 的 `<time>` 前缀），不进入 wire 路径；组合序镜像 wire 洋葱序——后注册的 decorator 改写先执行，故 preview 按注册逆序应用，有非交换双变换 parity 测试钉住两种路径输出一致）、窄 port（`SessionPort`、`ToolHost`、`StoreRegistry` 含 `forAgent(agentId)` 作用域；`PathRule` 定义在 `access/path-category.ts`——语义归属 access，kernel 仅 type 引用，避免 store→access→kernel→store 的类型环）、`EventMiddleware` 事件管线、开放 `ContextBlock { kind, render() }`（替代封闭 union）与 `TurnHooks`（beforeTurn/afterTurn/onReload，afterTurn 接收最小 `TurnEventAppender`）。`capabilities/*` 是能力模块（fs / skill / changelog / render / agent-mgmt / interaction / data / trigger / mcp / attachments / compaction / time-perception / memory），每个只依赖 kernel 类型。`assembleProject`（`factory.ts`）是唯一装配点——新增能力 = 新目录 + 装配点一行；`createProject` 为其兼容导出
- **会话运行时**：`SessionManager` 是纯 session 池（构造只收成品 `RuntimeDeps` + 可选 `RunConfigHolder`，无默认装配——所有依赖经 `createRuntimeDeps` 在装配点构造；职责为 session map 生命周期、可写 restore 前的幂等 legacy 迁移、hot-reload 标记，以及 `setDefaultModel`/`setSampling` 经 RunConfigHolder 单点更新派发）。`AgentRunner` 直接作为会话对象并持有 `SessionEventLog`：user/assistant/tool result 与 turn 边界同步追加到 per-agent SQLite events 表，`deriveMessages(events)` fold 结果单向同步给 pi 的 `agent.state.messages`，内存数组可随时丢弃重建。retry 追加 `turn/retried`（失败回复历史仍保留），compaction capability afterTurn 追加 `compaction/applied` 重启点并记录 sanitize 排除的 tail seq；restore 先确保 legacy 历史已在单事务中迁移，再 repair 未闭合 turn 并 fold 重建。事件直播仍经 EventPipeline（log → capability middleware → attachment sanitizer → 持久化翻译）输出，WS 协议不受存储格式影响。触发器 ⇄ 会话循环依赖经 `SessionPort` 消解（factory 先构造 SessionManager，port 为普通对象，capability 经 `init(services)` 接线——无 setter、无 ref 缝合）
- **运行时模块架构**：core 对外暴露 `ProjectRuntime`（轻量协调层，聚合 `ProjectManager`、`SessionRuntime` 与 capabilities 数组；`triggerManager`/`timerService` 为 derived getter（从 capability 派生，server 读取兼容），无具名双轨字段），`deleteAgent`/`shutdown` 遍历 capability 生命周期钩子（`onAgentDeleted` 可异步、`onAgentConfigChanged(agentId, kind)` 统一配置变更信号——kind 判别 `"mcp" | "tools" | "profile"`，经 `dispatchAgentConfigChanged` 广播给全部 capability，无鸭子类型嗅探；未来动态 tool 载入等运行时配置变更复用同一信号）；`ProjectManager` 是数据访问门面（执行「server 不得见 store 实例」边界），与 capabilities 的行为贡献互补
- **导出收紧**：store 层只导出 `ProjectStore`（供 core 内部使用），其余 store 类不对外暴露；core 的 `index.ts` 只导出外部实际消费的符号（model-providers 仅导出 `ModelCatalog` 与 images 静态目录——chat catalog 的可变全局 facade 已退役，所有权在组合根）。Server 无法直接访问 store 实例；文件写入统一走 `ProjectManager.writeFile/writeBinaryFile` 门面（内部 = resolveProjectPath + serverAccessPolicy.assertWrite + per-path FileWriteMutex + fs 写），server route 不再直接持锁写盘，与 LLM `write_file` 在同一把锁上按路径串行（锁只保证不撕裂，语义冲突由前端 dirty 状态 + fs.watch 兜底）。门面覆盖：`writeFile` / `writeBinaryFile`（编辑保存、主题、附件上传）、`createEntry(rel, mkdir|touch)`（文件树新建）、`deletePath`（文件树删除、附件删除——缺文件为 no-op）、`copyFileWithin`（图片导出）——全部 = resolveProjectPath + serverPolicy + per-path mutex
- **Store 树状结构**：store 按「聚合根 → per-agent 子 store」的树状结构组织——`ProjectStore` 作为聚合根持有 `ProjectConfigStore`、`SkillStore` 和 `Map<agentId, AgentStore>`；每个 `AgentStore` 聚合 per-agent 的 `AgentProfileStore`、`SessionStore`、`TriggerStore`、lazy 初始化的 agent-level `SkillStore`（指向 `{agentDir}/skills`）与 lazy 初始化的 `McpConfigStore`（读写 `{agentDir}/mcp.json`）。store 在构造时就确定自己的文件路径，运行时不做 agentId → 目录的查找
- **Store 只管存储**：store 是对存储层读写的抽象，不持有运行时状态（如活跃的 pi-agent-core Agent 实例）
- **thin aggregator**：聚合根（`ProjectStore`、`AgentStore`）只持有子 store 并暴露 getter（`projectStore.config`、`agentStore.sessions`），不逐个 wrap 子 store 的方法
- **结构化日志**：core 使用 pino 记录结构化日志，采用共享单实例注入模型——core 作为 library 只定义 `Logger` 类型和内部兜底工厂 `createSilentLogger`，实际的生产 logger 由 server composition root（`createServerLogger`）创建并通过 `assembleProject` 注入。AgentRunner 在 turn 中经 `logEventMiddleware` 记录 agent loop 全生命周期事件（agent_start/turn_start/tool_execution 等），stores 在关键操作（init/create/persist）中输出日志
- **AgentProfile**：业务层 agent 概念，从 `.spherse/agents/{agent-slug}/profile.md` 解析而来，包含不可变 `id`（UUID）、`createdAt`（创建时间）和 `slug`（目录名）
- **Agent context**：agent profile 的 `context` 字段声明项目内相对路径，构建 system prompt 时读取这些文件并注入 `Pre-loaded Context`
- **AgentProfileStore**：per-agent，首次读取无 `id` 的 profile.md 时自动生成并回写 `id`，创建 agent 时自动写入 `createdAt` 且更新时保持不变；支持 `getRawContent()` 获取原始 Markdown 内容用于编辑；`AgentStore.saveProfile()` 在写盘后同步刷新内存缓存的 `_profile`，避免后续 `getProfile()` 返回编辑前的旧数据（直接调底层 store 的 `save()` 只写盘不刷新缓存）
- **工具分配**：agent profile 未声明 `tools` 时默认不分配任何工具（空列表）；前端新建 agent 时通过模板默认勾选全部工具
- **工具集合（capability 聚合）**：工具由各 capability 的 `tools(host: ToolHost)` 贡献，`agent-assembly` 聚合为 `toolMap` 后按 profile.tools 过滤；`ToolHost`（agentId/sessionId/projectRoot/projectStore/fileWriteMutex/stores/pathRules/toolCatalog + per-session approvalGate/askGate）是工具可见的全部环境。`fs`（read/write/edit/list/search/move/copy/generate_image）、`skill`（load_skill + skill-catalog block）、`changelog`、`render`、`agent-mgmt`（manage_agent）、`interaction`（run_command/ask_user）、`project-config`（manage_project_config——读取/设置项目级配置，当前支持欢迎页路径；写路径复用 `ProjectConfigStore.updateWelcomePageSettings` 的校验与落盘，不经审批包装，主题 CSS 由 fs 工具直接写 `.spherse/theme.css`）、`data`（read_data/query_data/mutate_data——`*.data.json` 的 outline/局部读/manifest 入口读写，DataStore 单例由 `assembleProject` 创建并挂 `ProjectRuntime.dataStore`，与 fs 工具共享 `FileWriteMutex`，SDK 写入经 server `/data/*` 路由汇入同一实例，原子落盘 tmp+rename、锁内 RMW、内容哈希 version + ifVersion、幂等 key）、`trigger`（emit_trigger_event/manage_trigger）、`memory`（memory_save/memory_recall）。危险工具经 `withApproval` 包装（`run_command`、`manage_agent`/`manage_trigger` 的写 action，`shouldApprove` 谓词只对写 action 请求确认）。`manage_agent` 的工具名校验用运行时 `toolCatalog`（assembly 聚合后回填）——新 capability 的工具自动被认识，无需改中心名单。MCP 工具在运行时合并：mcp capability 的 turnHooks 按**配置版本**记忆（`configVersion(agentId)`，`invalidate` 时 bump；hook memo 对版本键，配置变更后下一 turn 自动重合并；`updateAgentMcp` 经 `onAgentConfigChanged(agentId, "mcp")` 统一信号触达全部 capability）——首个 turn 前按 agent 连接所有 enabled 的 MCP server（连接按 agent 缓存、跨会话共享），将发现的工具以 `mcp__{server}_{shortid}__{tool}` 命名追加进 `agent.state.tools`，同时把 server instructions/resources/prompts 渲染为 `<mcp-context>` block 注入 system prompt
- **运行时控制请求（control request）**：`SessionControlBus`（`packages/core/src/session/control-bus.ts`）提供 session 执行中途 core 向 renderer 请求并等待响应的通用机制——以 `requestId` 为 correlation key、`kind` 判别请求类型（`"approval"` 与 `"question"`，未来可扩展 steering 等）。`run_command` 的逐次人工确认为 approval kind：`withApproval` 包装器在 `execute` 前经 `ApprovalGate` 发起请求，bus 经 eventSink 发 `control_request` 事件，renderer 按工具选择卡片，用户决策经 chat WS 的 `resolve_control_request` 回传，`resolveControlRequest` → `bus.resolve` 唤醒等待中的 execute。审批等待超时 5min 自动拒绝；`abort()` 调 `bus.rejectAll` 全部失败。`ask_user` 工具是 question kind：经 `AskGate` 发起，renderer 渲染 QuestionCard，回答回传 `{ answer }`，超时（默认 600s，`timeout_s` clamp 60–3600）resolve `{ timedOut: true }`；`abort()` 与审批共用 `rejectAll`。事件经 `AgentEventHandler`（`AgentEvent | SessionControlEvent`）与 chat WS 透传，server 不解释 `kind`
- **run_command 安全模型**：进程以用户完整系统权限运行、**无 OS 级沙箱**（路径沙箱 `resolveProjectPath`/`llmAccessPolicy` 仅约束文件类工具，对子进程的文件/网络访问无效）。唯一硬屏障是 CommandCard 内联逐次人工确认；辅以 per-agent opt-in（默认关闭）、cwd 允许用户主目录内任意路径（`~` 展开，词法边界，仅防无心之失）、stdout/stderr 截断 100KB、超时（默认 60s，上限 1800s）自动 kill 进程树、AbortSignal 随 session 中断杀进程。OS 沙箱经评估永久放弃
- **路径安全与访问策略**：项目内路径通过 `utils/path-safety.ts` 的 `resolveProjectPath` / `isPathInside` / `assertInsideProject` 校验穿越边界。`access/path-category.ts` 的 `categorizePath(rel, extraRules?)` 将路径分类为 `PathCategory`（内置类别由 `PATH_PATTERNS` 定义），capability 可注册 `PathRule { match, category, llm: { read, write } }`（类型定义于 `access/path-category.ts`）——注册规则优先匹配且**自带完整读写裁决**，新增能力无需修改中心白名单（如 memory 的 `.spherse/agents/*/memory.jsonl`）。`access/access-policy.ts` 提供 `llmAccessPolicy(rootPath, deniedPaths, extraRules?)` 与 `serverAccessPolicy(rootPath)`；策略依次完成穿越校验 → deniedPath 校验（仅 LLM）→ 规则/类别白名单校验，`assertRead`/`assertWrite` 拒绝时抛 `AccessDeniedError`，`canRead`/`canWrite` 返回 boolean。**裁决优先级（声明式契约）**：用户 deniedPaths > capability pathRules > 内置类别白名单——用户 deny `.spherse` 会连带禁用依赖其路径的能力持久化（如 memory 的 memory.jsonl 写入），这是有意的安全优先语义；**pathRules 仅作用于 LLM 端**（`serverAccessPolicy` 不消费 extraRules）——capability 私有文件对 server 路由不可写，如需开放应经 PM 门面方法显式授权
- **写入互斥**：`FileWriteMutex` 由装配点创建唯一实例，经 ProjectStore（→ SkillStore/AgentStore）、ProjectManager、SessionManager 全链路注入；`write_file`、`edit_file`、`append_changelog`、`move_file`、`copy_file` 共享之，避免同一文件并发写导致内容丢失；`generate_image` 写入唯一时间戳文件名（`.spherse/generated-images/{utc}-{hex}.{ext}`），无同路径并发，不使用 mutex
- **删除 agent**：compound operation，由 `ProjectRuntime.deleteAgent` 协调——SessionRuntime.evictAgent 清理活跃 session、mcp capability invalidate 关闭该 agent 的 MCP 连接缓存、各 capability 的 onAgentDeleted 清理（trigger capability 删除该 agent 的 trigger 状态）、ProjectManager.deleteAgent 删除数据
- **Agent 配置热重载**：用户编辑 agent profile 后（经 `ProjectRuntime.updateAgent` → `ProjectManager.updateAgent`），`ProjectStore` 发出 `agent_updated` 事件。`SessionManager` 构造时订阅该事件，对所有属于该 agent 的活跃 `AgentRunner` 调用 `markReloadPending()`。下次 `sendMessage` 或 `retryLastTurn` 时检测到 pending 标记，先执行 `applyReload()`——从磁盘重新读取 profile，重建 systemPrompt + tools + streamFn（含 timePerception 包装），并经 `turnHooks.onReload()` 通知能力重置 memo 状态（如 mcp 合并标记）——再继续正常 prompt 流程。reload 失败时保留旧配置不中断对话。进行中的响应不受影响，配置在下一轮用户消息时才生效
- **附件处理（Attachment）**：`AttachmentProcessor` 端口定义在附件域 `attachments/index.ts`（kernel capability.ts 仅 type-only 引用），处理器由 capability 贡献（`attachmentsCapability` 贡献 image 处理器——从磁盘路径读取 base64 ImageContent；无全局注册表，新增类型 = 新 capability）。`AgentRunner.sendMessage` 接收可选 `Attachment[]`，经 `prepareAttachmentUserMessage(text, attachments, root, processors)` 组装多模态 user message 给当前 LLM turn；events 表只写 `stripUserAttachments` 生成的纯文本 + `_attachments` 路径引用。base64 仅在本轮 `agent.prompt()` 参数和 pi 内存中短暂存在，EventPipeline 中的 attachment sanitizer 同时保证对外 AgentEvent 不含 base64；finally 将 pi 内存替换为 stripped 版本。附件文件落盘于 `.spherse/attachments/`。时间感知同为 capability，通过 streamDecorators 向 outgoing messages 注入 `<time>` 感知前缀；compaction capability 基于 fold 后有效消息计划压缩（`compaction/summarize.ts` 复用 agent 实例的 `streamFunction` 发起请求前缀复刻式 LLM 摘要——decorator 链（含时间前缀）天然复刻、命中 provider prompt cache；失败时按 token 水位分层回退——≤ 90% window 跳过本轮、> 90% 回退机械 digest），并将 `sanitizeToolCallPairs` 排除的 seq 随 `compaction/applied` 持久化（含 `digestSource` 来源标记），fold 恢复时保持旧行为。
- **Skill 系统**：skill 分三层——builtin skill（来自 `@spherse/presets` 的 `PRESET_SKILL_SOURCES`，内存只读，随 app 升级更新）、project skill（主目录 `.spherse/skills/*/SKILL.md`，并兼容发现项目根目录 `.agents/skills/*/SKILL.md`）和 agent-level skill（`.spherse/agents/{slug}/skills/*/SKILL.md`，per-agent 私有 skill，由 `AgentStore` 的 lazy `SkillStore` 管理，无 builtin 来源）。三者均为 YAML frontmatter + Markdown body；frontmatter 可携带可选 `version`（semver，市场技能用于更新比较；本地手动创建的技能无此字段）。skill capability 在 `contextBlocks` 中合并三层 skill catalog，按 name 去重，优先级 agent-level > `.spherse/skills` > `.agents/skills` > builtin；`load_skill` 工具按同一优先级解析。`SkillDefinition` 的 `source` 字段（`builtin` 或 `project`）标识来源，两个 project 目录与 agent-level 均标记为 `project`。磁盘 skill 目录可携带附加文件（references/*、scripts/* 等），`SkillStore` 递归枚举填入 `SkillDefinition.files`，`load_skill` 加载时输出文件清单供 agent 用 `read_file` 读取。`SkillStore` 同时拥有 skill 的写逻辑（createSkill/installSkill，经 FileWriteMutex 串行化，zip-slip 防护，冲突报 `ConflictError` → server 409）；所有 UI/API 写操作仍只以 `.spherse/skills` 为目标，`.agents/skills` 仅作为兼容发现源；`installSkill` 支持 `{ overwrite: true }` 覆盖安装（新目录解压校验通过后旧目录移 tmp 备份、原子替换、失败回滚）
- **技能市场**：前端入口在 skill panel 三点菜单「技能市场」，打开 `MarketplaceDialog`（卡片网格，按 name 匹配本地技能推导安装/更新/已安装三态——本地无 version 或版本不可比时不提供更新，避免误覆盖手动技能；版本比较用 `lib/semver.ts`）。市场数据链路：`GET /api/projects/:projectId/marketplace/skills` 返回 OSS manifest（`marketplace.ts` service 代理，30s 内存缓存，contract schema 校验，URL 常量可经 env `SPHERSE_MARKETPLACE_MANIFEST_URL` 覆盖）；安装走 `POST /api/projects/:projectId/skills/marketplace-install`，body 仅 `{ name, version }`——server 从 manifest 解析 zipUrl（同源 SSRF 校验：zipUrl origin 必须等于 manifest origin）→ 下载到 tmpdir（50MB 上限）→ `installSkill(zip, { overwrite: true })` → 清理 tmp；请求 version 与 manifest 不一致返回 409（manifest 恰好更新，前端提示并 refetch）。manifest 与版本化 zip 由独立资源仓库 `spherse-assets` 的 GitHub Actions 手动发布到 OSS（`spherse/skills/manifest.json` + `spherse/skills/{name}/{version}/{name}-{version}.zip`，diff 基于 SKILL.md frontmatter version，内容变更必须 bump version）
- **触发器系统**：`TriggerManager` 是 trigger 域的公开门面（CRUD 委派 `TriggerStore`，写路径同步 scheduler 状态并 emit `trigger_updated`；执行/生命周期事件转发自 `TriggerExecutor`），内部组合两个单一职责模块：`scheduler.ts`（时间调度状态机——nextFire 缓存 + gc + due 检测，`now` 可注入故可假时钟测试）、`executor.ts`（`fire()` 执行引擎——session mode 路由 + 执行日志 + inProgress 防重入，reusable 绑定直接走 store 原语**不再 emit `trigger_updated`**——该事件恢复「用户显式变更」单一语义）；`TimerService` 归 trigger capability 所有（经回调驱动 `onTimeTick`，单个 `setTimeout` 链式轮询，间隔 10 分钟，首 tick 对齐到最近 10 分钟整数倍）。`TriggerManager` 以磁盘为唯一真相源，每次 `onTimeTick()` / `onUserEvent()` 从磁盘读取各 agent 的 `triggers/index.yml`。Trigger 分 `time`（cron）和 `event`（用户事件）两种。event 有两个发送端：客户端经 ws-bus 调用 `onUserEvent`（含 UI SDK action），以及 agent 经 LLM tool `emit_trigger_event` in-core 直调。`payload` 为字符串，经 `{{payload}}` 注入；`sp:` 前缀内部保留
- **memory 能力（per-agent）**：memory capability 为每个 agent 提供私有 JSONL 记忆存储（`.spherse/agents/{dir}/memory.jsonl`，惰性打开，append-only），贡献 `memory_save`/`memory_recall` 工具与 `<memory>` context block（注入当前 agent 最近 20 条记忆，per-agent 作用域经 `stores.forAgent` 隔离）；`MEMORY_PATH_RULE` 自带 LLM 读写裁决。agent 需在 profile `tools` 中显式启用
- **AI 文件访问限制**：项目配置可声明 `aiAccess.deniedPaths`，同时禁止 AI 读取和写入这些路径。`llmAccessPolicy` 基于规则 + category 白名单控制 AI 工具的读写范围——LLM 写白名单为 `userFiles` + `projectTheme` + `skills` + `agentTheme` + `agentSkills`（+ 注册规则的 `llm.write`），使 AI 可直接创建/修改 project 与 agent-level skill；`.spherse/` 下未分类的 catch-all（`spherseOther`）default-deny，避免内部数据泄漏；`list_files`/`search_content` 递归时用 `shouldSkipDirEntry` 统一跳过 dotfile、`node_modules`、`.git`
- **项目欢迎页设置**：项目配置可声明 `welcomePage.path`，保存项目根目录内 HTML 或图片相对路径；该设置不注入 agent prompt，也不影响 AI 工具访问策略。用户经项目设置 dialog 写入，agent 经 `manage_project_config` 工具写入（同一 `ProjectConfigStore` 真相源）；`.spherse/project.yaml` 已纳入 fs-watch watched-category，配置变更（无论来源）会推送 bus 事件，renderer 由 `WelcomePageQueryBridge`（ProjectScope 挂载、任意路由常驻）失效缓存并重新解析
- **预置内容注入**：`assembleProject` 检测到新项目时调用 `initPresets()`，根据 `PRESET_AGENTS` 配置自动创建预置 agent 并创建空的 `.spherse/skills/` 目录。当前内置一个预置 agent「小助手」（`templates/preset-agents/assistant.md`）：通用型助手，默认开启除 `run_command` 外的全部工具（含 `manage_agent`/`manage_trigger`/memory/manage_project_config；写操作仍受审批门控）。builtin skill 不注入磁盘，由 `SkillStore` 运行时从 `PRESET_SKILL_SOURCES` 内存合并。预置 agent 仅首次创建注入，已有项目不受影响

## Server 层

- **单 Fastify 实例**：整个应用只启动一个 Fastify 实例承载所有项目，由 `createMultiProjectServer()` 创建；不再为每个项目创建独立 server
- **ProjectRegistry**：`registry.ts` 维护 `Map<projectId, ProjectContext>`，项目打开时 `register()`、关闭时 `remove()`；`ProjectContext` = `{ runtime, projectManager, sessionRuntime, triggerManager, projectId }`
- **projectId**：由 core 的 `ProjectConfigStore` 在 `.spherse/project.yaml` 中生成（8 位 nanoid），跨重启和路径变化稳定；复制目录导致 id 冲突时 registry 静默改写副本的 project.yaml
- **路由按业务域拆分**到 `routes/` 目录，由 `routes/index.ts` 聚合注册；所有项目级路由统一使用 `/api/projects/:projectId/...` 前缀，`preHandler` 钩子从 registry 解析 projectId 并注入 `req.projectCtx`；全局端点（如 `/api/settings/providers`、`/api/settings/image-providers`）不带 projectId
- **API contract**：HTTP request/response 与 WebSocket message/event 的运行时 schema 定义在 `contracts/`，通过 `@spherse/server/contracts` 子入口导出给 server routes、WebSocket handler 和 renderer API client 复用；边界 JSON 进入业务逻辑前必须先通过 contract helper 解析；chat WebSocket 的 `ChatServerEvent` 是严格的 pi-agent lifecycle 事件 union（agent_start/turn_start/message_start/message_update/message_end/turn_end/agent_end/tool_execution/error 等）外加 session 级控制事件（`control_request`/`control_resolved`，带 `kind` 判别，由 `SessionControlBus` 产生而非 pi-agent-core），renderer 的 chat event 类型直接复用该 contract；client→server 方向除 `message`/`abort`/`ping` 外还有 `resolve_control_request`（回传审批决策）、`retry`（重试上一个失败的助手回复轮次）与 `withdraw`（撤回最后一轮 user 消息，server 广播 `turn_withdrawn` 锚点事件）
- **运行时 schema**：有 body 的 HTTP route 通过 server contract 中的 TypeBox schema 绑定 Fastify `schema.body` / `schema.response`；所有 JSON route（GET 含）均绑定 `schema.response`，含 pi-agent 复杂嵌套对象（session messages、turn context）的端点改用 handler 内 `parseContract` 校验以避免 fast-json-stringify 误丢字段；contract 按业务域拆文件（`agents.ts`/`sessions.ts`/...），命名用资源+操作风格（`AgentCreateRequest`/`SessionListResponse`）；renderer 的 `api.ts` 对每个响应统一走 `parseApiResponse` 校验；WebSocket 收到的 JSON 必须通过 contract parser 校验，非法消息返回统一 error event
- **内容 API**：`content.ts` 负责目录列表、文件读取、保存、删除、新建文件和新建目录；所有文件路径都通过 `serverAccessPolicy` 校验穿越边界与 category 白名单——GET 走 `.assertRead()`，POST/PUT/DELETE 走 `.assertWrite()`；server read 白名单为 `userFiles` + `rootIndex` + `changelog` + `projectTheme` + `generatedImages` + `attachments` + `skills` + `agentTheme` + `agentSkills`，server write 白名单为 `userFiles` + `rootIndex` + `changelog` + `projectTheme` + `skills`。文件读取时通过 `isBinaryBuffer`（前 8KB 采样 null-byte 嗅探）检测二进制文件，二进制文件返回 `binary:true` + 空 content（不再以 UTF-8 强解出乱码，也不把大文件整块读进内存），前端 Content Browser 据此渲染占位卡（`UnsupportedFileCard`）。`skills` 类别（`.spherse/skills/**`）经 server 读写放行，使项目技能面板可复用通用 content API 浏览/编辑技能文件；技能文件夹级生命周期（创建/安装 zip）由专用 `POST /skills`、`POST /skills/install` 路由委派 `ProjectManager`/`SkillStore` 处理（`ConflictError`→409、`ValidationError`→400）；市场安装由 `routes/marketplace.ts` 的 `GET /marketplace/skills`（manifest 代理）与 `POST /skills/marketplace-install`（远程 zip 下载 + 覆盖安装）提供
- **文件树 API**：`file-tree.ts` 返回面向 UI 选择的项目文件列表，通过 `utils/fs-walk.ts` 的 `shouldSkipDirEntry` 过滤 dotfile/dotdir、`node_modules`、`.git`（含 `.spherse`）
- **预览 API**：`preview.ts` 为本地 HTML、图片、字体与音视频内容提供预览 URL，renderer 通过 iframe、图片或 HTML card 使用。支持 mp3/mp4/wav/webm/ogg/flac/mov 等音视频 MIME 类型，并对所有 binary 响应附带 `Accept-Ranges: bytes`、支持 HTTP Range 请求（206 Partial Content），使 `<audio>`/`<video>` 可拖动进度条
- **WebSocket**：`ws-chat.ts` 推送 agent 对话事件（`/ws/projects/:projectId/chat/:agentId/:sessionId`，双向、session-scoped）；连接建立时 `restoreSession` 若因致命错误（agent/session 不存在等 `NotFoundError`）失败，以语义化 close code（`CHAT_CLOSE_CODES.SESSION_UNRECOVERABLE = 4401`，定义于 `contracts/websocket.ts`）关闭，前端据此阻断重连；瞬时错误以 `1000` 关闭触发前端重连。`sendMessage` 路径的错误不关闭连接，转为 error 事件（携带结构化 `code: ErrorEventCode`，如 `MODEL_NOT_CONFIGURED` / `PERMANENT` / `TRANSIENT`，由 `classify-run-error.ts` 按错误类型/status 判定）发回前端，前端按 code 做 i18n 渲染与重试决策；`ws-bus.ts` 是全局多路复用 bus（`/ws/bus`），将 trigger 事件、agent 元数据变更（`agent` 通道，`agent_updated` 事件，由 `ProjectStore` 在 agent 创建/更新/删除时发出，经 `ProjectManager.onAgentChange` 订阅）、fs-watch 文件变更、debug 日志四条 server→client 推送通道合并到单一连接上，客户端通过 `subscribe`/`unsubscribe` 消息按 `(projectId, channel)` 动态订阅子通道；`fs-watcher.ts` 提供按项目引用计数的共享 `fs.watch`（多订阅者共享 1 个 OS watcher），其过滤决策基于 core 的 `categorizePath` 的 watched-category 集合（`userFiles`/`rootIndex`/`changelog`/`projectConfig`/`projectTheme`/`agentTheme`/`skills`），并对 `node_modules`/`.git` 任意路径段降噪；项目技能面板的技能树刷新与 Files 面板一致，统一走该 fs-watch 通道（不使用主动 refreshKey）；bus envelope 与各通道事件 type/payload 的运行时 schema 统一定义在 `contracts/bus.ts`
- **触发器 API**：`trigger.ts` 提供触发器 CRUD 和手动触发（`/triggers` 增删改查、`/trigger-logs` 运行日志、`/run` 手动触发）
- **图片导出 API**：`images.ts` 提供 `POST /api/projects/:projectId/images/export`，将 `.spherse/generated-images/` 下生成的图片复制到用户选择的项目内目标路径；src 和 dest 均通过 `serverAccessPolicy` 校验穿越边界与 category 白名单
- **项目 settings API**：`settings.ts` 暴露 `/api/projects/:projectId/settings/ai-access` 读写项目级 AI 读取禁止列表，暴露 `/api/projects/:projectId/settings/welcome-page` 读写项目级欢迎页路径；`settings.ts` 还暴露 `/api/projects/:projectId/settings/theme` 读写项目级主题 CSS（GET 返回 `{ ok, content }`，文件不存在时 content 为空串；PUT body `{ content }` 原样落盘，返回 `{ ok }`）；`settings.ts` 同时承载全局 provider 列表端点（文本 `GET /api/settings/providers`、图片 `GET /api/settings/image-providers`）；renderer 不直接通过 content API 编辑 `.spherse/project.yaml`
- **MCP 连接器 API**：`agent-mcp.ts` 暴露 `GET/PUT /api/projects/:projectId/agents/:id/mcp`。GET 委派 `ProjectManager.getAgentMcp`（经 `McpConfigStore.getConfig` 读 `mcp.json`），PUT 委派 `ProjectRuntime.updateAgentMcp`（保存后经 `onAgentConfigChanged(agentId, "mcp")` 统一信号使该 agent 的连接缓存与 merge memo 失效——下一 turn 自动重合并新配置）。contract schema（`mcpServerConfig` 判别联合、`agentMcpResponse`、`agentMcpUpdateRequest`）定义在 `contracts/agents.ts`

## Electron 层

- **环境隔离**：`electron/bootstrap.ts` 作为构建入口，dev 模式（`app.isPackaged === false`）下将 `userData` 重定向到 `Spherse-Dev/` 目录，使 dev 和 prod 的 electron-store、localStorage 等所有数据完全隔离，可同时运行；`NODE_ENV=test` 时保留测试启动参数指定的 `userData`，确保 E2E 用例隔离
- **IPC handler** 集中在 `electron/ipc/` 目录，按业务域拆分为 project、settings、updater、debug、skill
- **preload** 是安全桥梁，声明 Renderer 可用的 IPC 方法白名单
- **项目 server 管理**：单一 Fastify 实例在 `app.whenReady()` 时通过 `ensureServer()` 启动一次，项目打开/关闭只操作 `ProjectRegistry`（register/remove），不再 create/close Fastify；`electron/server.ts` 暴露 `ensureServer`、`registerProject`、`unregisterProject`、`getServerPort`、`stopServer`
- **设置持久化**：`electron/settings.ts` 使用 electron-store 保存打开项目、最后活跃项目和 `AppSettings`（统一 schema：`locale` + `models: { text: ModelGroupSettings, image: ModelGroupSettings }` + 可选 `customProviders: CustomProviderDef[]`（用户自定义 OpenAI 兼容供应商定义，无密钥；仅文本 tab；可选 `contextWindow`/`maxTokens` 供应商级限长，应用于该供应商全部模型，留空回退 `CUSTOM_PROVIDER_DEFAULTS` 的 131072/131072（128k；maxTokens 与 contextWindow 相等时由 pi-ai 按剩余上下文收紧，即不设人为输出上限））+ 可选 `debugToolsEnabled`（控制 Debug Tools 入口可见性）+ 可选 `theme`（`"light"` | `"dark"` | `"system"`，默认 `"system"`，由「设置 > 通用 > 外观」切换），每个 group 含 `defaultModel`、per-provider `apiKey`，文本 group 另含可选 `sampling: SamplingParams`（`{ temperature?: number; topP?: number }`，未设字段代表「恢复 provider 默认」））。保存设置后同步到进程环境变量：文本 provider key 按 `PROVIDER_ENV_KEYS` 映射（如 `OPENAI_API_KEY`），图片配置写入 `SPHERSE_IMAGE_MODEL`（`"provider/modelId"` 格式）和 `SPHERSE_IMAGE_API_KEY`；API key 输入框显示掩码（前 4 后 4），保存时空串跳过、含 `****` 保留旧值。自定义供应商不走 env，而是由 `applySettingsToEnv` 末尾调用 core 的 `syncCustomProviders(defs, apiKeys)`（启动时 `restoreEnvFromSettings` → 注册在 `ensureServer` 之前；自定义 apiKey 复用同一 providers map 的 mask/merge），其 auth 用闭包直取 apiKey（keyless 本地服务器返回占位 key）
- **外观模式切换**：用户可在「设置 > 通用 > 外观」选择浅色 / 深色 / 跟随系统（`AppSettings.theme`）。Electron main 在启动（`restoreEnvFromSettings`）与每次保存设置时调用 `nativeTheme.themeSource = theme`，renderer 侧的 `@media (prefers-color-scheme: dark)` 与 Tailwind `dark:` 工具类据此生效——因此 CSS 变量、项目级 `.spherse/theme.css`、agent 聊天主题中现有的 `@media (prefers-color-scheme: dark)` 规则全部自动跟随应用选择的外观模式，无需额外改造
- **Provider catalog**：`core/model-providers/index.ts` 从 pi-ai `builtinModels()` / `builtinImagesModels()`（`@earendil-works/pi-ai/providers/all`）实例化的 module 级 **Mutable** 单例 `models` / `imagesModels` 动态生成 provider catalog——文本 catalog 由 `getSupportedProviders()` 经 `ENABLED_PROVIDERS` 过滤内置 provider（14 个 provider：openai/anthropic/google/deepseek/zai(Zhipu)/minimax/minimax-cn/xiaomi/moonshotai/moonshotai-cn/xai/openrouter/kimi-coding(Kimi For Coding)/opencode-go），图片 catalog 由 `getImageSupportedProviders()` 聚合所有已注册图片 provider（OpenRouter 内置 + 智谱）。智谱图片 provider 通过 `createZhipuImagesProvider()`（`model-providers/zhipu-images.ts`）以 `createImagesProvider()` 工厂构建，模块加载时 `setProvider` 注入 `imagesModels`。`PROVIDER_ENV_KEYS` 映射文本 provider→env key，`IMAGE_PROVIDER_ENV_KEYS` 映射图片 provider→`SPHERSE_IMAGE_API_KEY`。用户自定义 OpenAI 兼容供应商通过 `syncCustomProviders(defs, apiKeys)` 在运行时以 `createProvider()` + `MutableModels.setProvider()` 注入 `models` 单例（id 带 `custom-` 前缀避免与内置冲突），其 `getSupportedProviders()` 段在内置循环之后追加并标记 `custom/keyless/baseUrl`；内置 provider 仍 env-var 驱动不受影响
- **模型解析与默认模型切换**：模型 id 由 `resolveEffectiveModelId(profile, globalDefaultModel)` 解析（`profile.model || globalDefaultModel || undefined`，用 `||` 而非 `??` 使空串视为未配置）。模型解析延迟到 `sendMessage`：`buildAgent` 在无模型时构造一个不携带 model 的 Agent（`initialState.model` 可选），session 可在无模型状态下打开存活；`sendMessage` 前由 `ensureModelForAgent` 守卫，无模型或不可解析时抛 `ModelNotConfiguredError`（被 `ws-chat.ts` 的 catch 转为 `{type:"error", code:"MODEL_NOT_CONFIGURED"}` error 事件发回前端，连接不关闭）。SessionRuntime 暴露 `setDefaultModel()` 方法，IPC save-settings 后通过 `electron/server.ts` 的 `updateDefaultModel()` 同步更新运行时的 `globalDefaultModel`（仅文本模型注入运行时；图片模型经 env 注入，`generate_image` tool 从 `process.env` 直读，不经运行时）。对活跃会话即时生效：setter 遍历 `activeSessions` 重新解析并热替换 `agent.state.model`（下一轮生效，进行中的响应不受打扰）；profile 显式指定 `model` 的 agent 不受全局默认变更影响。模型未配置时 setter 跳过该 agent（不抛错），待用户配置后自动同步
- **模型采样参数（SamplingParams）**：采样参数（temperature、top_p）是与 `defaultModel` 同级的全局默认，统一收进 `AppSettings.models.text.sampling: SamplingParams`（`{ temperature?: number; topP?: number }`，每个字段可选，未设代表「恢复 provider 默认」）。传播链路：IPC `save-settings` handler **无条件**调用 `electron/server.ts` 的 `updateSampling()`（与 `updateDefaultModel()` 的 `if (defaultModel)` 守卫不同，因为 undefined 即「恢复 provider 默认」语义需要传播）→ `ProjectRegistry.setSampling()` → 各 project 的 `SessionManager.setSampling()`；registry 同时缓存当前 sampling，后续 `register()` 的新项目在 `createProject` 时传入。注入点：`SessionManager.buildAgent()` 调用 `getChatStreamFn(ctx.sampling)`，后者按字段分发：`temperature` 是 pi-ai typed `StreamOptions` 字段，直接注入 options；`topP` 因 pi-ai 无 typed 字段且 `buildBaseOptions` 是 allowlist 会丢弃未知 key，改用 `onPayload` 回调按 `model.api` 分支注入（`openai-completions`/`openai-responses`/`anthropic-messages` → 根级 `top_p`；`google-generative-ai` → `config.topP`；未知 api → no-op）。对活跃会话即时生效：`setSampling` 遍历 `sessions` 重赋每个 agent 的 `agent.streamFn = getChatStreamFn(ctx.sampling)`（下一轮生效）；仅文本路径生效，图片走 env 不涉及采样参数；`ModelGroupSettings.sampling` 经 `mergeModelGroup` / `maskModelGroup` 透传（incoming 覆盖 prev，undefined 即清除），否则会被 API key 掩码逻辑丢弃
- **时间感知（Time Perception）**：agent profile 的 `timePerception` 配置（per-agent）启用后，Agent 在对话中看到的时间线可与真实世界不同步。感知时间由纯函数 `perceivedMs = startMs + (realMs - epochMs) × flowRate` 从每条消息的真实时间戳推导。注入点在模块级函数 `composeStreamFn(sampling, timePerception)`：对 base streamFn（`getChatStreamFn`）可选地包装 `wrapWithTimePerception`，在调用 LLM 前对 context.messages 中每条 **user** 消息注入 `<time>感知时间</time>` XML 标签前缀（运行时计算，不修改 `agent.state.messages`，不持久化）。`buildAgent` 和 `applySampling` 统一调用 `composeStreamFn`，确保构建和热更新一致。只注入 user 消息以避免 LLM 从 assistant 历史中模仿输出时间标签；system prompt 的 `<session-context>` 注入 `time-perception: enabled` 标记及"Do not output `<time>` tags"指令。Trigger 系统、存储时间戳、日志全部保持真实墙钟——感知时间仅影响 LLM 看到的消息内容
- **图片生成配置**：图片模型与 API Key 存于全局 `AppSettings.models.image`，经 env 注入（`SPHERSE_IMAGE_MODEL` / `SPHERSE_IMAGE_API_KEY`），core `generate_image` tool 从 `process.env` 直读并通过 `getImagesModels().getModel(provider, modelId)` 统一解析模型（OpenRouter / 智谱走同一 `imagesModels` 单例），不经工具上下文 getter；「是否启用」隐式判断（provider + model + key 三者齐）
- **开发调试**：debug IPC 暴露 DevTools、electron-store 查看、reload renderer、reset app data 等动作；Debug Tools 入口（activity bar 的 Bug 图标）默认仅在开发模式（`!app.isPackaged`）可见，生产用户可在「设置 > 通用」开启 `AppSettings.debugToolsEnabled` 后显示（门控为 `isDev || debugToolsEnabled`）。Debug Tools 包含 Streaming Log 面板（可拖动悬浮窗口，通过 `/ws/debug` WebSocket 实时显示 server 日志）和 Turn Context 下载（通过 `GET /api/debug/sessions/:id/turn-context` 导出当前 session 的 system prompt + messages + tools 为 JSON 文件，便于排查 agent 行为；messages 为 LLM 投影后的真实请求上下文——复用 `agent.convertToLlm`（contextProjectors + 角色过滤）并应用 capability 的 `previewTransforms`（如 time-perception 的 `<time>` 前缀），而非原始 buffer）
- **App 更新机制**：`electron/updater.ts` 封装 `electron-updater`，通过 GitHub Releases 分发更新。`autoDownload` 和 `autoInstallOnAppQuit` 均关闭，全程需要用户主动同意（同意下载 → 下载完成确认重启）。启动后延迟 5s 静默检查（`main.ts`），静默检查的 `update-not-available`/`update-error` 事件被 `silent` 标记抑制不推给 renderer，仅 `update-available` 弹窗。平台差异：Windows 客户端代码走完整 electron-updater 流程（check → download via CancellationToken → quitAndInstall），但 CI 自 OSS 镜像改造（ba8c049）起统一 `--publish never`、不再上传 `latest.yml`，Windows 更新检查因缺少 feed 会报 `update-error`（恢复需按双 arch 设计 updater channel 文件，见 backlog）；macOS 未签名阶段走通知模式（GitHub Releases API 版本比较 + release notes 展示 + `openExternal` 跳转下载页，不下载安装）。`checkForUpdates` 在 dev 模式（`!app.isPackaged`）直接返回 upToDate。IPC 契约以事件流为唯一真相源：`invoke` 只触发动作返回 void，`webContents.send` 推送 5 个事件（`update-available`/`update-not-available`/`download-progress`/`update-downloaded`/`update-error`），preload `onUpdateEvent` 注册监听并返回 unsubscribe 函数。renderer 侧 `useUpdateChecker` hook 用 `useReducer` 管理状态机（idle/checking/upToDate/available/downloading/downloaded/error），`errorPhase` 区分检查失败与下载失败。CI（`.github/workflows/build-and-release.yml`）由 git tag 触发，`create-release` job 先行创建 Release，mac（arm64/intel）与 win（x64/arm64，arm64 在 x64 runner 上交叉打包，better-sqlite3 直接拉取 `win32-arm64` electron prebuild）并行构建，统一 `--publish never` + `gh release upload` 上传安装包（mac 重命名为带 arch 后缀的 `.dmg`，win 产物名含 arch：`Spherse-Setup-{version}-{arch}.exe`）；`publish-oss` job 汇总上传阿里云 OSS 并生成 `latest.json`（`win.x64`/`win.arm64`，arm64 对旧版本 release 缺失时省略；读取端兼容旧 manifest 的 `win.setup`）；末尾 `deploy-web` job 在 tag push 且 `publish-oss` 成功后用 `gh workflow run deploy-pages.yml --ref <发版tag>`（job 级 `actions: write` 权限；GITHUB_TOKEN 触发的事件默认不级联 workflow run，但 `workflow_dispatch` 是官方例外）联动部署 web 版（GitHub Pages：landing + web），保证 Pages 内容与发版代码一致；`workflow_dispatch` 手动重发布（re-publish OSS 资产）不触发 Pages 部署

## 前端路由与状态

- **Hash Router**：renderer 使用 React Router Hash Router，路由表达应用内导航状态，避免 Electron 本地页面刷新时依赖服务端 history fallback
- **项目路由**：项目、会话和内容页通过 URL 表达，当前路径形态为 `/project/:projectId`、`/project/:projectId/chat/:sessionId`、`/project/:projectId/content?path=...`
- **projectId**：URL 中使用 `.spherse/project.yaml` 中的稳定 id（nanoid 8 位 token）作为路由参数，替代旧的基于目录名生成的 projectKey；全链路（core → server → IPC → renderer 路由 → localStorage key）统一使用 projectId 作为唯一身份标识
- **项目内 lastRoute**：每个打开项目的子页面路由持久化在 renderer localStorage（`spherse:last-route:<projectId>`），不写入 electron-store。应用启动、项目切换和关闭当前项目后的下一个项目导航都会恢复该项目的 lastRoute；关闭项目时清理对应的 localStorage key
- **应用级 store**：`app-store.ts` 管理打开项目集合、当前项目、restore/open/close/reveal 等 Electron IPC 相关动作，并持久化左侧 side panel 固定/自动收起偏好
- **服务端状态缓存**：renderer 根节点挂载 TanStack Query；`queries/project.ts` 统一管理按 project 隔离的 agents、sessions 与 session 分页缓存、mutation 后失效、bus/reconnect 刷新和 UI SDK 的命令式缓存访问；`queries/content.ts` 按 project + path 缓存文件内容、目录列表和完整文件路径索引，使主内容页、浮窗、文件树与文件搜索共享请求和快照。`ContentQueryBridge` 将 fs-watch/reconnect 集中转换为 cache invalidation，树的展开/选择及编辑器 draft/conflict 仍保留为本地交互状态。关闭项目时移除对应 project query cache。`project-data-store.ts` 不再复制服务端快照，只保留初始消息与 streaming session id 等前端运行时投影。
- **项目 UI store**：折叠状态、浮窗会话状态等纯 UI 状态按 projectId 管理，通过 renderer localStorage 持久化。折叠状态在 `features/agent-session-list/store.ts`，浮窗会话状态在 `features/floating-chat/store.ts`，浮窗内容浏览器（多窗口，按 projectId → filePath 映射）在 `features/floating-content-browser/store.ts`。浮窗 chrome（拖拽/调整大小）由共享的 `components/floating-frame/` 提供，floating-chat 与 floating-content-browser 通过 `hookPrefix` 参数复用并各自生成 `data-chat-float-*` / `data-content-float-*` 主题钩子
- **局部状态边界**：文件编辑 dirty/conflict、弹窗表单等短生命周期状态保留在对应组件或 feature hook 内；Chat 输入框草稿按 sessionId 缓存在 renderer `localStorage`，用于 session 切换和应用重启后的草稿恢复；欢迎页设置与主题设置 dialog 的打开状态保留在 `ActivityBar` 内（通过「设置」二级菜单触发，仅 active 项目可见）；设置读取走 TanStack Query（欢迎页 `queries/welcome-page`、主题 `queries/theme-settings`，保存经 facade 写后失效缓存，外部文件变更经各业务域自己的 QueryBridge（`ThemeQueryBridge`/`WelcomePageQueryBridge`，fs-watch/reconnect → invalidate，ProjectScope 挂载）与 `useCustomTheme` 的 `<link>` 重挂各自响应；bridge 数量增多时可再收敛为统一注册层）
- **项目级 sessions 批量接口**：会话目录聚合走 `GET /api/projects/:projectId/sessions?perPage`（方案 B：每 agent 取前 perPage 条归并排序，`byAgent` 携带 per-agent `{hasMore, loaded}` 游标）；core `ProjectManager.listProjectSessions` 跨 agentStore 聚合，server 薄路由仅 clamp perPage 到 [1,100]；renderer `queries/project.ts` 的 `useProjectCatalog` 一次调用拿全目录（sessions 查询不依赖 agents 查询完成），分组「加载更多」与 deep-link 回退（缓存未命中时单次 `perPage=100` 查找 + 逐 agent getSession 探测）复用同一端点；既有 by-agent 端点保留给 UI SDK、load more 与单会话 CRUD
- **Trigger 查询层**：triggers 真相迁入 TanStack Query（`queries/triggers.ts`，`GET /api/projects/:projectId/triggers` 归并列表 + select 按 agent 过滤/派生指示器）；`useTriggerStore` 仅保留事件驱动运行态（running 标记 + triggerEventVersion 日志重拉信号）、`handleTriggerEvent`（completed → refreshProjectSessions）与 `runTrigger` store action（乐观标记/失败回滚——run 属运行态操作，不经查询层）；`TriggerEventBridge` 是 trigger 域的唯一事件接线（该域带运行态，不适用纯失效 QueryBridge 模板）：updated/completed/failed → invalidate + running 增删 + completed 通知/refreshHistory，triggered 纯运行态不失效，重连补偿失效缓存并清空 running 标记（missed completion 不重放且 server 无对账端点）；CRUD mutation facade（create/update/delete/resetBinding）写后失效；`project-data-store` 不再持有 hasEnabledTriggers 投影
- **Chat run / WebSocket 生命周期**：Core `AgentRunner` 只拥有 agent 上下文、执行与消息持久化，通过单次 `sendMessage` callback 输出事件（并发 turn 有 in-flight guard，二次调用抛 ValidationError）；server `ChatSessionHub` 按 project/session 建立 transport channel，独立负责共享 restore、当前 run 状态、事件广播、压缩事件快照和无 attachment 时的空闲释放。hub 实例由 `server/index.ts` 创建并共享给 `ws-chat.ts` 与 sessions 路由：UI SDK 的静默发送（`sendMessage` 带 `open:false` 且目标会话未 attach WS 时）走 `POST /api/projects/:projectId/agents/:agentId/sessions/:id/messages`，经 hub 的 `startDetachedRun`（fire-and-ack：restore ready + running 检查后启动 run 即返回，run 失败仅 log + 向 subscriber 发 error 事件）在同一 channel 上执行，与已打开的 WS 共享 run 序列化并 fan-out 事件；channel running 时返回 409。WebSocket 是 channel 的可替换 attachment，socket close 只解除 attachment；若 agent 正在运行，Core run 会继续执行并持久化消息，重连后由 hub 先重放当前 run 快照，再发送 `run_status` 对账运行状态。WebSocket 连接具备心跳保活与指数退避重连（1/2/5/10/30s）：每 30s 发 ping，只有连续 60s 等不到 pong 才关闭；renderer suspend 导致 timer 大幅跳跃时会重置探测窗口，避免恢复后误判超时。socket 发送失败被隔离在 server attachment 边界，Core 则保证 `message_end` 先持久化再回调，连接故障不能打断 agent 或阻止最终消息落库。
- **Chat streaming store / runtime 边界**：`features/chat/runtime/streaming-store.ts` 只维护 UI 可观察的 session 状态与公开 actions；每个 session 的 WebSocket、心跳、重连 timer、连接期事件缓冲和重连历史对账由同目录下非响应式 `ChatSessionRuntime` 持有，并通过 `ChatRuntimeRegistry` 管理生命周期，transport 对象不进入 Zustand。`connectionStatus` 表达 socket 的 disconnected/connecting/open，`historyStatus` 独立表达 pending/syncing/ready，因为连接状态与历史是否已经成功对账是正交维度。`useChatSession` 只负责 attach/detach 与选择状态，切换页面或关闭 chat 不会中断后台流式输出。正常断线保留 streaming 和未完成消息，只有致命连接错误或服务端 `run_status: inactive` 才结束前端运行态。WebSocket 事件按 animation frame 批量归约，避免高频 token update 触发过多 React render；`features/chat/model/chat-session-reducer.ts` 仅负责实时事件到 view state 的纯数据归约，历史解析/稳定 ID 合并位于同目录 `chat-history.ts`，实时与历史共用的 tool/card 投影位于 `chat-tool-projection.ts`；`agent_end` 时继续通过 `lib/aggregate-file-changes.ts` 聚合本次 run 的文件变更。**失败/错误重试与韧性**：错误分两条来源——Source 1（`sendMessage` 在 `agent.prompt()` 之前抛错，如 `ModelNotConfiguredError`，经 `ws-chat.ts` 的 `classify-run-error.ts` 判定 `code` 后发 `error` 事件，用户消息未落库）与 Source 2（pi-agent-core `handleRunFailure` 吞掉异常、emit 合成 `message_end`(`stopReason:"error"`)，用户消息已落库）。reducer 用 `_turnError` 标记区分：`message_end`(error) 与「`error` 事件落到 streaming 气泡」置 true（Source 2），`error` 事件新建空气泡不置（Source 1）。重试决策是纯函数 `features/chat/model/retry-plan.ts`（`planRetry` 返回 `retry-last`/`resend`/`none`，`shouldAutoRetry` 判瞬时额度），store 的 `executeRetry` 只执行 plan；Source 2 走 client→server `retry` 消息（服务端 `AgentRunner.retryLastTurn`（先消费 pendingReload）弹出失败助手消息 + 删 DB 行 + `agent.continue()`），Source 1 / 发送失败（`_sendFailed`）走重新 `sendMessage`。瞬时错误（`code:TRANSIENT`）由 store 自动重试（backoff `[2s,5s]`，上限 2 次，`maybeAutoRetry` 用 `autoRetrying` 标记独占退避窗口、`streaming` 防 run 重入），耗尽或永久错误落错误气泡 + 手动重试按钮。韧性增强：断连横幅（`ConnectionBanner` 读 `connectionStatus`/`reconnectFailed`）、历史对账失败带退避重试 + `historyError`、重连达上限停止 + 手动重连、`onerror` 主动 close 消除僵尸 socket、`respondApproval` 返回值校验 + toast。**消息撤回**：最新未失败（非 `_sendFailed`）user 消息气泡在非 streaming 时提供撤回按钮，发送 client→server `withdraw`；hub 侧不经过 `startRun`（不产生 `run_status`，运行中返回 ConflictError），成功后 Core `AgentRunner.withdrawLastTurn` 追加 `turn/withdrawn { seq }` 锚点事件（废弃区间 `[seq, 本事件 seq)` 由 fold 推导，agent 上下文经 `syncBufferFromLog` 同步移除；末轮已被 compaction digest 覆盖时拒绝），并向 channel 广播 `turn_withdrawn`；前端不做乐观删除，reducer 收到广播后丢弃最后一条 user 消息起的尾部（含错误气泡），store 以 `pendingWithdraw` 标记将撤回失败的 error 气泡置为不可重试（`_withdrawError`），避免重试把刚想撤回的消息重新发送。
- **Chat 历史懒加载与对账**：聊天历史按消息条数分页（默认每页 20 条，`?limit=&before=` cursor），attach 与每次重连时加载最新一页。新格式会话先将完整 events 投影为带 seq 的可见历史再切片；`id` / `oldestId` 语义为事件 seq。legacy 会话仍以 messages.id 走只读旧路径（SQL `LIMIT` 取数）。两条路径都在页首为孤儿 toolResult（其 toolCall 的 assistant 消息在更早处）时向后扩展页边界，保证单页内 toolCall/toolResult 配对自洽——前端按页解析消息且跨页合并不重新配对，页原子性由 server 保证。分页 contract shape 保持 `{ entries: [{ id, message }], hasMore, oldestId }`，前端加载与重连对账无需区分两种存储格式。
- **Chat 自动滚动（CSS column-reverse 方案）**：消息列表容器 `MessageList` 使用 `flex-direction: column-reverse`（DOM 顺序 newest→oldest，视觉上 newest 在底部、oldest 在顶部），`scrollTop=0` 即「底部」。流式 token 到达时末条 assistant 消息在底部增长，`scrollTop` 保持 0 → **浏览器原生逐帧贴底，无需 JS 节流滚动**（取代了旧的 1s 节流 `scrollIntoView` + `stickToBottomRef` 方案）。用户向上滚动阅读历史时 `scrollTop<0`，新内容仍在底部生成，依赖 Chromium 默认 `overflow-anchor` 保持阅读视口稳定，自动跟随与阅读历史天然解耦、不再互相打架（load-more 的 prepend 路径因 `overflow-anchor` 在 `column-reverse` 下不可靠，改用上条所述的显式捕获/恢复，不依赖浏览器 anchoring）。「回到底部」FAB 显隐由单一阈值判定：`scrollTop >= -NEAR_BOTTOM_THRESHOLD(100px)` 即视为贴底（`isNearBottom`）。仅保留两处 JS 介入滚动：用户发送消息时强制 `scrollToBottom("smooth")`（`scrollTo({top:0})`）覆盖阅读状态；FAB onClick 同样调用 `scrollToBottom("smooth")`（不透传 React 点击事件，避免其被当作 `behavior` 参数）。session 切换时按 store 中的 `scrollPosition` 恢复位置（通过 `scrollTopRef` 在卸载时持久化；column-reverse 下保存的 `scrollTop` 为距底部偏移，语义与恢复一致；该恢复与 load-more 恢复同在 `useLayoutEffect` 中执行，规避 keyed remount 下被动 effect cleanup 读取已脱离 DOM 的 `scrollTop=0` 问题）。注意：DOM 顺序为 newest→oldest，屏幕阅读器会从最新消息读起（当前为已知取舍）

## i18n

## 前端样式

- **基础组件层**：前端基础 UI 统一使用 shadcn/ui 本地源码组件，组件位于 `packages/app/src/components/ui/`，当前底层 base 为 Base UI
- **组件生成配置**：`packages/app/components.json` 记录 shadcn 样式 preset、Tailwind v4 CSS 入口和 `@/*` alias
- **单一 Token 体系**：所有 design token 统一使用 Spherse 自有命名空间（`--sp-*`），CSS 变量定义在 `styles.css` 的 `:root`，暗色模式通过 `@media (prefers-color-scheme: dark)` 覆盖。组件 Tailwind 类名（`bg-background`、`text-foreground` 等）**不动**——通过 Tailwind `@theme inline` 桥接层（`--color-background: var(--sp-background)`）解析，与源变量名解耦。不维护旧的自定义变量（`--surface`、`--base` 等已移除），旧的 shadcn 组件库前缀变量已全部更名为 `--sp-*`
- **Spherse 业务 token**：shadcn 语义未覆盖的业务语义按需新增 `--sp-{name}` 变量 + `--color-{name}` Tailwind 映射（如 `--sp-success` / `--sp-success-foreground` / `--sp-warning` / `--sp-warning-foreground` / `--sp-diff-added`），注册后业务组件可用 `text-success`、`bg-warning` 等 Tailwind 类
- **样式写法**：所有样式通过 Tailwind 工具类写在组件 className 中，不在 `styles.css` 中新增手写 CSS class。禁止硬编码颜色值（如 `text-[#333]`），需要新颜色时在 `styles.css` 中注册 CSS 变量 + Tailwind 颜色
- **语义 Token 使用**：使用 shadcn 语义 token（`bg-background`、`bg-card`、`bg-muted`、`bg-primary`、`bg-accent`、`text-foreground`、`text-muted-foreground`、`border-border`、`text-destructive` 等）。Spherse 自有业务语义按需新增 `--sp-*` token
- **间距与阴影**：使用 Tailwind 标准 scale（`p-2`、`rounded-md`、`shadow-sm` 等），不硬编码 magic number
- **暗色适配**：业务组件不写 `dark:` 修饰符，由 CSS 变量值切换自动适配。仅 shadcn/ui 组件源码中已有的 `dark:` 保留
- **Markdown 渲染**：动态 Markdown 统一通过 `MarkdownContent` 组件映射 `react-markdown` 节点样式，不在 `styles.css` 里维护 `.chat-markdown` 或 `.prose-content` 选择器
- **三级主题层叠**：主题系统形成清晰的三级层叠（低 → 高优先级）——① App defaults（`styles.css` 内置 `:root` / `--sp-*` 变量）；② Project theme（`.spherse/theme.css`，经全局 `<link>` 注入 `document.head`，可同时承担「全局 UI 变量」`--sp-*` in `:root` 与「全局 chat 默认样式」`[data-chat-root] { ... }` 两个角色）；③ Agent theme（`.spherse/agents/{agent-slug}/theme.css`，chat 容器内后载入的 `<link>`）。三级主题均以 `<link>` 从 preview 路由载入（`href` 锚定在 `/preview/*` 文件服务树内），相对 `url()` 引用的图片/字体等资源因此能正常解析到项目文件。相同特异性的规则后者胜出（agent theme 的 `<link>` 在 DOM 中位于 chat 容器内，比 project theme 的 `<link>`（`document.head`）更靠后），agent theme 自然覆盖 project theme 的 chat 规则
- **项目级自定义主题**：用户可通过项目根目录 `.spherse/theme.css` 覆盖 CSS 变量实现项目全局主题定制，只允许覆盖 `:root` 中已有的变量名。应用内可通过项目头像右键菜单「设置 → 主题」打开 CSS 编辑器直接读写该文件。前端通过 bus 的 fs-watch 通道监听 `.spherse/theme.css` 变更（无论来源是 UI 保存、外部编辑器还是 LLM 工具修改），文件变更时 `useCustomTheme` 自动热重载 `<link>` 样式表
- **Agent 聊天主题（原生 CSS nesting）**：每个 agent 可在 `.spherse/agents/{agent-slug}/theme.css` 定义聊天窗口主题，采用**原生 CSS nesting**——最外层为 `[data-chat-root] { ... }`，内部嵌套各选择器自动作用域到 chat 内。废弃了自写的 `scopeCss`（`packages/app/src/lib/scope-css.ts` 已删除），用户直接写标准 nesting 语法，浏览器原生处理 `@media` / 嵌套 / 裸声明等所有情况。前端进入聊天页时将该文件以 `<link rel="stylesheet">` 形式从 preview 路由载入到聊天窗口内（`useAgentTheme` 构造 `href` 为 `.../preview/.spherse/agents/{agent-slug}/theme.css`，相对 `url()` 解析基址为 agent 目录，因此主题引用的本地图片/字体可正常解析），优先级高于项目级主题；该样式只作用于当前 agent 的聊天窗口，不影响侧边栏等外部 UI。inline chat 与 floating chat 共用同一份 CSS（由 `Chat` 组件统一载入，`[data-chat-root]` 块同时覆盖两者，floating 的 `data-chat-root` 嵌套在 `data-chat-float-root` 内），若需单独定制浮动窗 chrome 再加一个 `[data-chat-float-root] { ... }` 顶层块
- **Chat dark mode**：聊天主题暗色适配通过在 `[data-chat-root] { ... }` 内嵌套 `@media (prefers-color-scheme: dark) { ... }` 实现，浏览器原生处理嵌套 at-rule，dark mode 自动跟随 OS 切换，且作用域天然限定在 chat 内，不污染全局
- **Chat theme 自动重载**：server 端 fs-watcher 已将 `agentTheme` 纳入 watched-category 白名单，`.spherse/agents/*/theme.css` 变更会经 bus 的 fs-watch 通道推送事件；renderer 端 `useAgentTheme` 订阅该通道，命中后 debounce 并更新 `<link>` 的缓存破坏 query，触发样式表重新拉取，无需重开窗口即可看到效果（floating chat 主题由其内部渲染的 `Chat` 组件统一负责，不再单独订阅）
- **聊天/文档主题选择器**：应用根容器（整窗最外层，铺满视口且 `position: relative`）暴露 `data-app-root`，供项目级主题用 `::before` / `::after` 或固定定位层在窗口任意位置叠加全局装饰（背景纹理、角标、水印等）；聊天窗口对用户主题暴露 `data-chat-root`、`data-chat-header`、`data-chat-messages`、`data-chat-message[data-role]`、`data-chat-bubble`（消息气泡内容容器）、`data-chat-composer`、`data-chat-composer-input`（输入框外框）、`data-chat-float-close`（浮动窗关闭按钮）等入口；Markdown 元素暴露 `data-md-code`（代码块 `<pre>`）、`data-md-code-inline`（行内 `<code>`）、`data-md-quote`（引用），chat 与 document 视图共用同一组属性（作用域由主题作者用父选择器显式表达）；文档视图容器暴露 `data-content-doc`，供项目级主题精准定制文档视图 markdown 样式；项目面板暴露 `data-project-panel`，内容浏览器暴露 `data-content-browser`，供项目级主题定制这两个区域的背景与外观；全局 toast 暴露 `data-toast-root`（包裹 sonner 的 `position: fixed` 视口容器），供项目级主题用 `[data-toast-root]` 前缀 + sonner 原生 `[data-sonner-toast]`/`[data-type]`/`[data-title]`/`[data-description]` 等后代选择器定制 toast 外观。变更这些 DOM 入口、聊天布局或新增可主题化选择器时，需要同步更新 `packages/presets/templates/agent-theme-template.css`、`packages/presets/skills/spherse-create-agent-chat-theme/SKILL.md` 与 `packages/presets/skills/spherse-create-ui-theme/SKILL.md`

- **浮窗聊天**：会话可脱离主窗口进入可拖拽/可调整大小的 CSS overlay（Portal 渲染到 `document.body`，z-index 按 side panel pinned 状态动态切换——pinned 时 `z-50` 在面板之上，unpinned 时 `z-30` 在面板之下）。同一项目最多一个浮窗，新浮窗自动关闭已有浮窗。浮窗状态（sessionId、position、size）持久化在 `project-ui-store` 并写入 renderer localStorage。浮窗会话在侧边栏显示选中态，点击无响应；关闭浮窗后会话回到未选中状态。双击浮窗标题栏可关闭浮窗并导航到该会话的完整聊天页。浮窗聊天主题复用 Agent 聊天主题，通过 `data-chat-float-root`、`data-chat-float-titlebar` 选择器限定作用域。`FloatingChatManager` 渲染在 `ProjectLayout` 内，项目切换时随 `key={projectKey}` 完整卸载重建。文本选中发起的发送至当前会话列表包含浮窗会话，浮窗会话的发送不触发导航。
